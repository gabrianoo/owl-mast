# Unattended execution foundation (ENG-01)

`automation/unattended` is the smallest supported bridge between the GitHub backlog that owns engineering progress ([tracking contract](engineering-tracking.md)) and a T3 coordinator that dispatches story work. It is engineering automation, tracked in [ENG-01 (#106)](https://github.com/gabrianoo/owl-mast/issues/106), outside the OM product numbering. It does not run on its own: a T3 coordinator thread calls it between `delegate_task` turns. There is no loop, schedule or daemon, and the installed `bmad-loop` CLI is not used.

**Operating agreement (owner-accepted 2026-11-06, supersedes the strict prerequisites below as explicitly stated).** The owner accepted a trusted-machine agreement ([`spec-eng-01-trusted-operation`](https://github.com/gabrianoo/owl-mast/issues/106#issuecomment-6838323771), a spec comment on #106): the operator's development machine is trusted (worktrees isolate files, not host credentials); budgets are coordinator-enforced best effort (stop dispatch and request cancellation on expiry; a coordinator failure can leave a worker running); restricted credentials are used where practical and broad ones are disclosed as broad, never certified bounded; Project Status and acceptance stay manual owner actions and machine comments are evidence proposals. It supersedes the earlier requirement that hard child bounds, exhaustive credential-denial qualification and automated Project Status synchronization must precede all unattended work. It does **not** assert those guarantees exist, and accepting the risk is **not** activation: every real-transport state command stays refused and the default allowlist stays empty for this effort. Earlier results below are historical and keep their original labels.

## What GitHub owns and who writes what

| Fact | Where | Writer | Meaning |
| --- | --- | --- | --- |
| Stable ID, parent epic, `Depends on`, `Epic prerequisites`, tasks | Issue body | Owner through Git-revised specs | Specification. Read with a strict grammar (`None` or a comma-separated list of ids); anything else is unknown and blocks dispatch. |
| Project Status (`Backlog`, `Ready`, `In progress`, `In review`, `Blocked`, `Done`) | Project 2 Status field | **Owner only** | `Ready` = owner acceptance; `Done` = accepted completion. GitHub offers no compare-and-swap, so the machine never writes this field. It reads it for eligibility and treats any change as a stale revision. |
| Machine checkpoints | Issue comments `<!-- unattended kind=… run=… story=… op=… -->` | Machine, append-only | `claim`, `release`, `block`, `proposal`, `probe`. One comment per operation identity; a duplicate is a conflict. |
| Task checkboxes | Issue body | Owner | The `proposal` comment lists tasks with the exact commit; the owner ticks them. |
| Issue open/closed | Issue | Owner | Closing as completed is acceptance; any other or unknown close reason is not. |
| CI pass, review approval, merge, deployment | PR checks, PR reviews, merge, release | GitHub / reviewer / owner | Read, never written; each stays a distinct fact. |

Project Status synchronization is **not implemented**: there is no safe equivalent on GitHub's API. The owner moves Status by reading the machine's comments.

Dispatch is possible only when all of these hold: the story is in the policy allowlist; its epic is not E17/E19 (unless explicitly included); its Project item exists with a matching Stable ID; both declarations parse; Status is `Ready`; every `Depends on` story and every story of a prerequisite epic is `Done` **and** closed with the explicit reason `COMPLETED`. A story in `contract_design_exceptions` may run its designated design portion before prerequisites, flagged `dispatchable-contract-design-only`. Anything unknown fails closed.

## Commands

All commands print one JSON document. Global flags go before the command.

```sh
python3 -m automation.unattended verify-mapping            # 19/85/340 and relationships against live GitHub
python3 -m automation.unattended --policy automation/examples/first-run-om-01-02.toml plan   # dry run, writes nothing
python3 -m automation.unattended check-permissions         # basic_access observation; bounded and activation are never granted by this probe (exit 2)
python3 -m automation.unattended probe                     # environment probes from policy
python3 -m unittest discover -s automation/tests -t .      # qualification suite (fixtures)
```

State commands need `--run-id` (one path segment of lowercase `[a-z0-9._-]`, at most 64 characters, never `--`; anything else refuses `run-id-invalid` before any state is touched: state directories may live on a case-insensitive filesystem, and a marker value cannot carry `--`); `probe-write` needs it too and exits 2 when the probe is not idempotent. Anything that can reach a GitHub write also needs `--live` (`reserve`, `authorize-repair`, `propose-evidence`, `block`, `cancel`, `cancel-run`, `resume`, `rebase-revisions`, `probe-write`, `dismiss-claim`; the `--live` help is generated from that list). On the real transport a new run and every advancing operation need `--activation <file>` naming a current activation authorization; without one they refuse `activation-required` before any GitHub call. Only `reserve` creates a run: every other state command on a run that does not exist refuses with nothing written (`run-not-found`, or `run-metadata-missing` when its artifacts are retained; only when no activation is presented at all is `activation-required` reported first; the creation rules of a presented document, such as `activation-used`, `activation-window-short` or the evidence citations, apply to `reserve` alone, so a mistyped run id is reported as the missing run it is), so a report or a cleanup command never starts a run or spends an activation. Cleanup and `status` of a run that was activated earlier work on the run's validated recorded binding without the file (see below); a partial or foreign recorded binding refuses `activation-binding-invalid` and nothing is released. `status` is a locked state write (it records an observed expiry or clock regression durably); `status --read-only` is the monitoring form: the run is opened and reported without the store lock, without creating the state directory or the lock file and without any write, and a would-be stop is reported as `activation.would_stop`. State lives under `.unattended-runs/<run-id>/` (gitignored: `run.json` with its environment binding, `journal.jsonl`, `stories/<ID>.json`); a store-wide `fcntl` lock serializes every operation across processes. Budgets are derived from the story files under that lock; `run.json` counters are a cache for `status`.

```sh
U="python3 -m automation.unattended --live --run-id <run-id>"
E='{"taskId": "<id>", "status": "result_available"}'            # terminal evidence from task_status (or a terminal task_cancel result) for the ACTIVE task
$U reserve OM-01.02 --baseline <sha>                           # admission + implementer authorization BEFORE delegate_task (refused on the real transport unless --activation is current)
$U bind-receipt OM-01.02 --receipt receipt.json --worktree <path> --branch <branch> --authorization <id>   # consumes exactly that authorization (its id came from reserve) after delegate_task returned the task id
$U record-head OM-01.02 --sha <sha> --task-evidence "$E"       # the implementer task is terminal; its exact commit is recorded
$U run-checks OM-01.02 --sha <sha> --cwd <worktree>           # full configured set on the exact clean HEAD; the only check evidence
$U authorize-review OM-01.02 --sha <sha>                      # worktree re-read; reviewer authorization BEFORE delegate_task
$U bind-receipt OM-01.02 --receipt reviewer-receipt.json --worktree <reviewer's own path> --branch <branch> --authorization <id>   # consumes it; the reviewer's own checkout is verified and must differ from the implementer's; the receipt carries the authorized SHA
$U record-review OM-01.02 --sha <sha> --verdict approved|changes-requested --report <ref> --task-evidence "$E"
$U authorize-repair OM-01.02                                  # budgeted; required after any failure; at most two rounds, then blocked; then bind-receipt
$U record-task-terminal OM-01.02 --task-evidence "$E"         # release the active task without recording anything else (e.g. after an invalidation)
N='{"authorization": "<id>", "reason": "delegate_task was never called"}'   # no-launch attestation for an UNRESOLVED authorization (no receipt will ever come)
$U record-no-launch OM-01.02 --no-launch "$N"                 # resolve it; slot stays counted; nothing else changes
$U propose-evidence OM-01.02 --sha <sha> --pr <n> --task OM-01.02-T1 --summary "…"
$U cancel|block OM-01.02 --reason "…" [--task-evidence "$E"] [--no-launch "$N"]   # evidence required while a task is active; attestation (or the late receipt) required while an authorization is unresolved
$U cancel-run --reason "…" [--task-evidence '{"OM-01.02": {...}}'] [--no-launch '{"OM-01.02": {...}}'];  $U resume OM-01.02;  $U rebase-revisions OM-01.02 --reason "…"
$U status                                                     # locked report of an existing run; records an observed expiry or clock regression durably (a state write)
python3 -m automation.unattended --policy <policy> --state-dir <dir> --run-id <run-id> status --read-only   # monitoring form: no lock, no file created, no write; would_stop reported, not recorded (add --activation <file> to have the presented document compared too)
$U bind-receipt OM-01.02 --receipt '{...}' --for-cleanup --reason "…"   # the activation file is lost for good and the task was launched: bind it for cleanup only (exits 3, cleanup-requested; the reason is journaled; refused, cleanup-not-needed, while the run's current activation is presented), then cancel/block with its terminal evidence; --reason without --for-cleanup (reason-without-for-cleanup) or --for-cleanup without a reason (reason-required) is refused before any run is opened, so nothing is written
$U --activation <file> clear-clock-regression --clearance <owner clearance.toml>  # owner action by convention, journaled: clears a recorded clock-regression stop once the clock has caught up (see below); the clearance is kept outside --state-dir and outside every git work tree
$U dismiss-claim --issue <n> --comment-id <id> --reason "…" [--force]   # owner action under this run's CURRENT activation: a stray or forged claim marker stops counting for coordinators under this identity (journaled write-ahead with the evidence, idempotent); never this run's own claim, never a claim a run under this state directory still owns, and any other claim only when a run under this state directory proves it finished with the story or with --force (the reason attests its coordinator is dead: a claim's age proves nothing, a run past its wall clock still owns its story until its task finishes); deleting the comment is the other way
```

## Coordinator protocol (T3) and what is and is not established

1. `verify-mapping` and `probe` must pass; `check-permissions` must report `basic_access` (it never reports a bounded credential, see below).
2. `plan` decides eligibility from a fresh snapshot; a stable id carried by more than one issue (in the plan snapshot or the fresh read) is `ambiguous-identity` and admits nothing, and any unknown dependency fact (a dependency without a Project item or Status, an unknown close reason, a Done-but-reopened dependency, an unreadable declaration, a prerequisite epic with a story in any of those states) is `unknown-eligibility` before the contract-design exception can apply. `reserve` re-reads every revision the decision depends on (story, parent epic, dependency closure, Project items) under the store lock, checks GitHub for an active claim by any other coordinator on any other allowlisted story (`claim-active-elsewhere`: one active story at a time across state directories and machines), issues the implementer **task authorization** (counted against `max_delegated_tasks` from that moment, bound or not) and posts the claim marker **before** any task exists; an exhausted task budget refuses here, before any launch. After the claim lands the claims are read again, on this story and on every other allowlisted story, and the earliest wins, ordered asymmetrically so that an edit never produces two winners: another coordinator's claim counts from its creation (GitHub keeps `created_at` across edits, so an old comment edited into a claim marker is backdated and costs us our slot; the edit is reported and the owner clears it with `dismiss-claim`), ours from the later of its creation and last edit, an unparseable time fails closed the same way (a foreign claim wins, ours loses), then by comment id; when an earlier claim is found the claims are read once more and the win is taken only on the visible release of every earlier claim, so a loser still posting its release costs no one else a slot while a claim that merely vanished from one read still counts. A later claim on another story loses with `claim-active-elsewhere`, on the same story with `claim-race-lost`; that outcome is durable (`claim.race_settled`): a reservation whose re-read failed or whose process died is not reported as `reserved`, `bind-receipt` refuses it (`claim-race-unsettled`) and `resume` settles it first (a lost race cancels and releases), a reservation written before the flag existed included (`claim-race-flag-added`). A claim that cannot be read back is `conflict` (`claim-unverifiable`); `resume` re-reads it and, once visible, passes it through the same revision gate as a fresh claim (changed revisions cancel and release), restores the reservation (only to `reserved`) and settles the race.
3. `delegate_task` with `isolation: "worktree"`, `role: "implementation"`, target `claudeAgent` / `claude-fable-5-1` / `options {effort: "high"}`; `bind-receipt --authorization <id>` validates the receipt (exact model and effort, a task id never bound anywhere in the run: any story, any role, terminal or not), the worktree identity, consumes **exactly the named authorization** (a wrong or stale id is refused; a reviewer receipt records the SHA that authorization was issued for, never the current head) and makes the task the story's **active task**. One active story per run and one active task per story, enforced under the lock; a story is admitted at most once per run (no reclaim); an authorization binds once. **An issued authorization is an ownership obligation until it is resolved**: the tool cannot see whether `delegate_task` was called, so until the exact receipt arrives (and that task's terminal evidence follows) or the coordinator attests `record-no-launch` for that id, the story stays owned — `cancel`/`block`/`cancel-run` refuse with `authorization-unresolved` (and revoke the authorization so that no work is ever bound to it), no release is posted, no other story is admitted and no replacement authorization is issued. If the run stopped after the authorization was issued (cancelled, or past `max_wall_clock_minutes`), or the authorization was revoked, the receipt still binds but **for cleanup only**: the slot stays spent, the id stays bound, the task is owned until its terminal evidence, the phase does not advance and the command refuses with `bound_for_cleanup`, so the coordinator cancels the task instead of working it. A reservation that never returned (`claim-incomplete`) is the one case the state itself proves unlaunched.
4. `record-head` with the exact commit and the implementer's terminal evidence (`task_status` `workState: result_available` or a terminal `task_cancel` result), then `run-checks` in the claimed worktree. Checks fail ⇒ `authorize-repair` (round 1 or 2, counted at authorization, then `bind-receipt` of the new implementer task) or `block`; `record-head` after a failure without an authorized and bound repair is refused.
5. `authorize-review` only after the full configured check set passed at that commit, the worktree still reads that commit and is clean, and no task is active; then `delegate_task` with `isolation: "worktree"` for a fresh `codex` / `gpt-6-astra` / `options {reasoningEffort: "high"}` reviewer and `bind-receipt --worktree <reviewer's checkout> --branch <branch>` (the policy requires worktree isolation for the reviewer as for the implementer, and the receipt's isolation string proves nothing: the reviewer's own worktree is named, verified with the same identity check and refused when it is, or is nested with, the implementer's claimed worktree, `reviewer-worktree-shared`, so review evidence comes from a checkout independent of the tree under review; a review receipt that binds for cleanup only, after a revocation or a run stop, needs no worktree, since it authorizes no review and the reviewer's checkout is usually gone). `record-review` needs the reviewer's terminal evidence, binds the verdict to the commit and re-reads the worktree; any unreported change or a new commit invalidates check and review evidence and abandons a pending proposal, but never releases the active task; a pending review authorization is revoked, not abandoned, and its reviewer (if launched) must be bound and terminated, or attested unlaunched, before checks run or a new review is authorized for the new commit.
6. `propose-evidence` after approval: phase `review-approved`, approved and head SHA equal to the proposed commit, no active task, revisions unchanged, worktree re-read, PR head equals the approved commit, PR open and unmerged, every review page read, no reviewer with an outstanding `CHANGES_REQUESTED`, status check rollup exactly `SUCCESS` (`FAILURE`, `ERROR`, `EXPECTED`, `PENDING` and no checks at all refuse `pr-checks-not-successful`); posts the persisted proposal body and the `proposed` phase in one write. Merge, `Done`, Status and closing remain owner actions.
7. Terminal acknowledgement is not result evidence, and success must be identified and linked: only a `completed`/`result_available` terminal record of exactly the bound `(taskId, runId)`, recorded in the relevant role for exactly the authorization the coordinator selected (the latest consumed implementer authorization; for the reviewer, the one issued for exactly that SHA), is successful; `interrupted` (the real transport's status for a cancelled run), `failed` and `cancelled` release ownership but never advance. One common gate runs on **every** advancing consumer of recorded evidence — `record-head` (also its same-SHA no-op), `run-checks`, `authorize-review`, `authorize-repair`, `record-review`, `propose-evidence` and both `resume` proposal paths (a pending replay and a completed proposal whose transition did not persist) — whatever path led there: direct evidence, `record-task-terminal` then a reload, an upgrade from state an older coordinator wrote, or a restart. A head, check result, approval or posted proposal recorded by an older coordinator over an unsuccessful execution is history, never evidence: on `resume` a pending proposal is abandoned (nothing posted) and a landed one keeps its comment without advancing (`reconciliation-withheld`); `cancel`/`block` remain the way out. An absent run identity on the authorization or the record (`run-identity-missing`), a record for another run or none at all (`no-successful-execution`), a record whose role or `authorization` does not match the selected authorization (`conflicting-evidence`) and an unsuccessful or contradictory outcome (`worker-interrupted`/`worker-unsuccessful`) all refuse; task-only completion is never an identified execution. Legacy history without the `successful` flag is read from its status, and a flag that contradicts its status is unsuccessful; nothing is migrated or rewritten. `bind-receipt` and `reconcile-retained-execution` are ownership and cleanup, not evidence, and are not gated; the regression fixtures under `automation/tests/fixtures/legacy-bb4c3ee/` are states the pre-repair coordinator produced through its own commands (`automation/tests/legacy_baseline.py`).
8. Ownership is released only with terminal evidence for exactly the active task: `cancel`/`block`/`record-task-terminal` need `{taskId, status}` matching it (implementer evidence never releases a reviewer); an unresolved authorization is released only by its exact receipt plus that task's terminal evidence or by `record-no-launch` naming it (the coordinator's attestation, trusted like a receipt); `cancel-run` validates its evidence maps before marking the run cancelled, releases the stories that owe nothing and reports every story whose release refused, with its code (active task, unresolved authorization, mismatched evidence); a cancelled run, or one past its wall clock, refuses every advancing operation (no authorization is returned or issued; the pending slot stays spent) while still accepting terminal evidence and cleanup. The wall clock is a local expiry of this tool's authorizations; it does not stop a launched child. Cancelling or blocking a story abandons its pending advancing intents in the same write as the terminal phase. `resume` replays owed cleanups (release, block) first and unconditionally, then checks the worktree identity of an active story only, then reconciles a completed intent whose transition did not persist only where a fresh attempt would be allowed (run neither cancelled nor past its wall clock; a claim only with unchanged revisions, otherwise the story is cancelled together with the release it owes; a proposal only with phase `review-approved`, exact-SHA approval and head, no active task or unresolved authorization, and only after fresh revisions with unique identities, the re-read worktree and the PR re-verify, with the same consequences as a fresh proposal), otherwise keeps the effect as history without advancing or reposting (`cancel`/`cancel-run` finish the story); then it abandons advancing intents of a terminal story or a stopped run, re-validates the remaining ones (claim: revisions, changed ⇒ cancelled with its release when the claim comment landed; proposal: current phase and exact-SHA approval, revisions, worktree, PR) before posting their persisted payload, then refuses on changed revisions.

**What the installed T3 tools support and what remains.** The tool metadata supports the protocol above: authorization happens under the local lock before `delegate_task`; the receipt is bound afterwards; `task_status` reports `workState` (`working`, `waiting_for_children`, `result_available`) and the final summary; `task_cancel` stops the task's running and queued turns and its delegates and, per the coordinator's inspection of the tool metadata, reports `cancel_requested` or a terminal state. Under the accepted agreement the remaining facts are residual risks, not prerequisites: there is no hard deadline or resource bound on a delegated child (`timeoutMs` limits the wait in `mode: wait` only), no credential confinement (the child runs with the machine's credentials), and launches are invisible to the tool (it bounds what can be bound; receipts, terminal evidence and no-launch attestations are the coordinator's reports). No upstream T3 work is required for this agreement. What is still required before any activation is the engineering-only lifecycle smoke with real receipts (`automation/tests/lifecycle_smoke.py`, run by the coordinator, never by a unit test), its published evidence and a fresh independent review; until then nothing is activated: the unconditional `live-execution-disabled` refusal has been replaced by the explicit, run-bound activation authorization described [below](#activation-authorization-explicit-opt-in), and the shipped policy and committed candidate still dispatch nothing.

## Lifecycle smoke helper (manual steps, synthetic state)

`python3 -m automation.tests.lifecycle_smoke --dir <fresh dir> <operation>` performs one operation per invocation against a JSON-persisted fixture transport (no network, fixture environment, fixture-only story `OM-99.01` under epic `E99`) and the coordinator's own run store: `prepare` (synthetic backlog, policy allowing only `OM-99.01`, optional synthetic git worktree, reservation), `bind` (receipt to the exact authorization, `--source real|fixture`), `head`, `check` (the configured commands on the exact clean HEAD), `authorize-review`, `bind` (reviewer, with `--worktree`/`--branch` naming its own checkout), `review`, `cancel`, `terminal`, `restart` (fresh process reloads persisted transport and state and resumes), `status`. It never fabricates receipts or evidence: whatever the coordinator supplies is recorded verbatim with its declared source, so a published smoke counts as real only when the receipts and terminal evidence came from real `delegate_task`/`task_status`/`task_cancel` results and the review from a fresh GPT-6 Astra High task. Unit tests drive it with `--source fixture` and are labelled fixtures.

## Execution identity: (taskId, runId) pairs and the retained owner (third repair, 2026-11-07)

A resumed T3 owner keeps its task id and gets a new run id; `t3_thread_send` returns the run id only. Executions are therefore `(taskId, runId)` pairs: `taskId` stays the `task_cancel` handle and is never replaced by a run id; `runId` identifies the execution a receipt or terminal evidence is about. Canonical coordinator reports:

- Receipt: `{"taskId", "runId", "providerInstanceId", "model", "options", "isolation"}`. A fresh `delegate_task` receipt may carry the run as `childRunId` instead. A receipt naming two different runs is ambiguous and refused, except for a retained owner being re-run, where `runId` is the current run and `childRunId` the stale first run.
- Terminal evidence: normalized `{"taskId", "runId", "status"}`, or `task_status`-shaped `{"taskId", "workState": "result_available", "hasPendingChildRuns": false, "latestTerminalRunId", "latestTerminalStatus"}`. Only the latest terminal fields identify the terminal run; `childRunId`, `status` and `summary` are stale first-run fields and are ignored. Live or pending child work, a missing terminal run, `cancel_requested` or a run that differs from the bound execution refuses and keeps ownership.
- Retained owner: only the story's own implementer task (the one bound to its implementation authorization) may be bound again, only for a repair authorization, only with a run never bound anywhere in the run, and only after its previous execution is terminal. Reviewer tasks are never reused: a new run on an old reviewer task is not a fresh review. Legacy records without a run id are never completed by inference; a legacy active task without a run id stays owned and the missing fact is reported.

`reconcile-retained-execution` is the audited cleanup for the historical case (a revoked repair authorization whose task ran as a new run of the retained owner but was never bound): it needs the exact authorization id, a receipt of the retained owner naming that run with the dispatch record of the resumed run (`{"dispatch": {"runId", "messageId"}}`), `startedAt` at or after the time the clock read when the authorization was issued (`issued_observed_at` when `issued_at` was floored, otherwise `issued_at`; a run of the same task that started before that reading does not settle the authorization), matching terminal evidence, a reason and the provenance of the evidence, and the bound worktree/branch. The run-order check has a bound: when `issued_at` was floored, a `startedAt` from `issued_observed_at` up to `issued_at` is accepted by design. In that window (at most the 5-minute tolerance before the run's high-water mark, while the clock read behind the mark) a run that started before the issue on a correct clock cannot be told from one that started after the issue. What separates them there is the rest of the evidence: the run id that the receipt and its dispatch record name, which must never have been bound, and the provenance the operator states for it. It is cleanup for a stopped run only (cancelled, past its wall clock, under policy drift or under a recorded activation stop; a missing `--activation` does not make a run stopped; under a `clock-regression` stop the owner can still clear, a **revoked** authorization is reconciled, since it binds for cleanup only before and after a clear, while a pending one refuses `clock-regression`: clear the stop or cancel the run), reloads the run under the lock, resolves only that obligation (status `consumed`, cleanup only), writes a backup of the story file first, re-authorizes nothing, approves nothing, admits nothing, keeps the run cancelled and the budgets spent, and creates no no-launch attestation. Identical evidence (status, dispatch, timestamps, target, worktree) is idempotent; any difference is conflicting evidence and refuses. An ordinary `bind-receipt` of a retained owner whose history is legacy task-only is refused (`run-identity-missing`): the missing run identity is never guessed. The smoke helper exposes it as `reconcile` (with `--run-id` for a historical copy); the parent exercises it on an isolated copy before touching any historical state, and the unit suite replays it in CI on a committed, scrubbed copy of that pre-recovery backup (`automation/tests/fixtures/historical-eng01-trusted-20261106/`: the operator's home path relocated, the pickled transport converted to `transport.json`, nothing else edited). Recovery commands:


## Activation authorization (explicit opt-in)

The unconditional `live-execution-disabled` refusal is replaced by an explicit, run-bound **activation authorization**: a TOML file (`automation/examples/activation-om-01-02.candidate.toml` is the committed, **unapproved** candidate) passed as `--activation <file>`. Nothing is activated by default:

- Without `--activation`, no live run is created and every admitting or advancing state command on the real transport refuses `activation-required` before any GitHub call; on a run that was never activated this includes `status` and cleanup. The shipped `automation/policy.toml` keeps `allow = []`. The one exception is deliberate and listed below: cleanup and `status` of a run that **was** activated earlier work on its validated recorded binding without the file.
- The committed candidate has `approved = false`, a placeholder run id, a zero policy digest, placeholder evidence and an expired window; copied as-is it refuses (`activation-unapproved`, `activation-mismatch`, `activation-invalid`, `activation-expired`). `check-activation` reports exactly why without touching state or GitHub. It answers two questions: `can_create` (may this document create `--run-id` under `--state-dir` now; not when the run's artifacts are retained without `run.json`, `run-metadata-missing`, which `reserve` would refuse) and, when that run already exists, `current` (is this document that run's activation and can the run still advance under it: not cancelled, not past its wall clock, no recorded stop, and the host clock not more than the 5-minute tolerance behind the run's high-water mark, which the next locked operation would record as `clock-regression`; the question to ask about a running run); for a run that does not exist yet the two are the same. With `--run-id`, `--expect` is required (and refused without `--run-id`; `expect-required`, exit 3, a malformed call: exit 0 must answer exactly one question, so a mistyped or new run id can never read as "may advance"): `--expect create` exits 0 only when `can_create` (the go signal before `reserve` on a fresh run id), `--expect advance` only when the run exists and is `current`; anything else exits 2. The wall clock is judged as every locked operation judges it, on the later of the clock and the run's high-water mark. `stops` lists every refusal code, `creation_problems` the creation-only ones, `used` the use on record and `ledger_root` the ledger directory it was read from. Every report has the same keys, with `null` for what does not apply (no document presented: `activation`, `used`, `ledger_root`, `run_exists` and the like are `null`), and always carries `expect`. Without `--run-id` it takes no `--expect`, reports the `policy_digest` an activation must name, looks no run up and is current for nothing (exit 2): an activation authorizes exactly one run.
- An activation is **current** only when all of these hold at the moment of the operation: `approved = true`; `binding` names this repository, the canonical digest of the policy in use (`python3 -m automation.unattended --policy <file> check-activation` reports it as `policy_digest`, with or without an activation; comments and whitespace do not change it), `environment = "live"` and the exact `--run-id`; `scope.stories` lists each allowlisted story once, as strings, and equals the policy allowlist; `targets` and `budgets` equal the policy's (any model, option, isolation or budget drift refuses; both loaders refuse non-string target values and repeated stories, so `timeoutMs = 600000` is refused by the policy loader too); `issued_at <= now <= expires_at` with a window of at most 24 hours. Three more conditions hold only when a run is **created** and are never applied mid-run, so tightening them strands no run that already exists: `evidence` cites the published lifecycle smoke and fresh review as two different GitHub comment or review URLs on this repository (`issues/<n>#issuecomment-<id>`, `pull/<n>#issuecomment-<id>` or `pull/<n>#pullrequestreview-<id>`: reviews exist only on pull requests; the id is 1 to 20 digits, leading zeros included (a sanity limit), a longer one is not a citation, and neither is an id whose value is 0 (GitHub never issues it); the issue or pull request number `<n>` is a positive integer of at most 20 digits without leading zeros, so `issues/0`, `pull/0` and `issues/007` are not citations either (GitHub never issues number 0, and a leading zero would spell one publication two ways); two citations are the same when their numeric ids are equal, whatever the kind, the path or leading zeros; placeholders refuse; only the shape is checked, the tool never fetches the comment, so a well-formed made-up id passes and its content and author remain the approver's statement); the document has not created a run before (`activation-used`); and the remaining window covers the run's wall-clock budget (`activation-window-short`), so a run cannot be started only to expire partway through; a policy whose wall-clock budget does not fit inside one activation window (1440 minutes) can create no live run and says so.
- A live run is created only under a current activation and records its binding (id, file digest, approver, window) in `run.json`; `started_at` is the same validated creation observation as the binding's `validated_at`, sampled after the store lock is held. The loaded document is a cache: creation re-reads the source file under the store lock before anything is written, so a source that was changed, removed or made malformed after it was loaded creates no run (`activation-mismatch` / `activation-required` / `activation-invalid`, nothing written); reopening an existing run re-reads it too (`run-open`). The coordinator first checks without the lock, so these refusals leave no state directory behind; that check is advisory, and a creation that loses a race to another process is refused under the lock, after the state directory and its lock file exist.
- **One activation creates exactly one live run, per user account and machine.** Creation first writes a record to the use ledger, one file per document digest under `~/.local/state/owl-mast/activation-ledger/` of the account running the tool (a fixed directory outside every state directory and work tree; not configurable by a flag or an environment variable, which the unattended loop could set: the home directory is read from the account database, not from `$HOME`; a uid without an account entry, or an entry whose home directory is empty or relative, refuses `activation-ledger-unwritable`: such a ledger would follow the current directory). The ledger is per account and per machine: another account (sudo, a service account, a container uid), another WSL distribution, Windows Python or another host starts with an empty ledger and can create the run again from the same document; that, like the rest, is the trusted-machine convention (run the coordinator under one account on one machine), and `check-activation` (`ledger_root`) and `status` (`activation.ledger`) print which ledger was consulted. The ledger is keyed on the content, so a copy, a symlink, a hard link or another spelling of the path is the same approval; any later creation from it, with another `--state-dir`, another run id or after the run directory was deleted, refuses `activation-used` and names the use on record. A re-issued activation (any change, such as a later window) is another document with its own record, whatever its file name. The record is written crash-safely (temporary file, sync, exclusive link, directory sync), carries the absolute state directory, and has three states: `pending` (written before `run.json`), `committed` (after it) and `aborted` (writing `run.json` raised and the file is absent). Only an `aborted` creation may be retried, and only by the same creation: the same run id under the same state directory (the same real path, or the same directory by `os.path.samefile` when both exist; never by case-folding, since `State` and `state` are two directories on a case-sensitive file system); the retry sets it `pending` again, with `created_at` set to the retry (an unconfirmed refusal names the attempt that may have created the run), `first_attempt_at` kept and the attempt (`at`, `pid`, `source`) appended to `attempts` (the first attempt and the latest ten are kept; the attempt that failed carries its `abort_cause`; an `attempts` value that is not a non-empty list of records with an `at` makes the record unreadable, a use). A `pending` record without `run.json` is ambiguous (the process died between the ledger and `run.json`, or the run directory was deleted after a creation whose confirmation could not be written) and refuses `activation-used` as an unconfirmed creation naming its run id and state directory: the document is burned and is re-issued. This replaces the earlier rule that a creation which died in between burned nothing: an approval that might have created its run is never trusted to create it again. A confirmation that cannot be written is journaled (`activation-use-unconfirmed`, once per error type, errno and variant since the last `activation-use-confirmed` line; the message names a random temporary file and is kept as a non-key field) and retried by every later open of the run, which also confirms a `pending` or `aborted` record of that run. The line's detail carries `type`, `errno`, `strerror`, `field`, `error` and `consequence`. `strerror` holds operating-system text only, and not for every OS error: a failed read of the ledger file (`field` `file`) or a recorded directory that cannot be examined carries the text of that error beside its `errno`; a confirmation that could not be written carries it only when the error has no errno (it is then what tells two such errors apart) and `null` when it has one; every other condition carries `null`. `field` is the variant of a condition that is not a failed write and is part of the once-per key; `consequence` says what the condition means for the record: "stays pending, every later open retries" is said only of a confirmation that could not be written (an `OSError` or a refusal from the ledger). Two conditions that no write can fix are journaled the same way, each with its own consequence. A record of this run id under another state directory, such as a moved or copied one, is `state-dir-mismatch`, and `field` says what the recorded path holds now, each with its own advice: `recorded directory holds the run` (`<recorded>/<run-id>/run.json` exists: opening the run through that directory confirms the record), `recorded path exists without the run` (an unrelated directory, or something that is not a directory, sits there: the record cannot be settled from here, the document is spent, and moving the run back is the only way to confirm it), `recorded directory gone` (said only when the path does not exist: same consequence, move the directory back) and `recorded directory cannot be examined` (any other error, such as a permission problem on a parent, with its `errno` and `strerror`, or a recorded path that is not absolute, which is never resolved against the current directory: whether the run is still there is not known, and it is never reported as gone). A record that is damaged or cannot be read is `ledger-unreadable`, a use: a record without a state directory, with an empty or malformed `attempts` history, or whose `state` is missing or not one of `pending`, `committed`, `aborted` (`field` names `state_dir`, `attempts`, `state` or `record`), and a ledger file that is not JSON, such as a torn one (`field` is `json`, `errno` is `null`); the `activation-used` refusal names the field that failed, and the consequence says the record is damaged, not pending: no open repairs it. A read the operating system refuses (`field` is `file`, with the `errno` of the read error, so a permission problem and a disk I/O error are two lines) is worded apart: the message says the record cannot be read, without claiming the file exists (a directory on its path that cannot be searched refuses the same way), and the consequence says that what the record says is unknown while it cannot be read, that every later open tries again, and that until then it is a use. An open that finds the record of this run id `committed`, whatever state directory it names (restored by hand, or committed through the directory it was created under, which also settles the `state-dir-mismatch` line of a copy), settles the unconfirmed lines still on record with an `activation-use-confirmed` line, so a later recurrence is journaled again. A line written before `field` existed carried the variant in `strerror`; the older variants `unreadable` and `recorded directory exists` match no present key, so after an upgrade such a condition, if still present, is journaled once more. Every non-creating open of an activated run whose journal has no `run-started` line (the creation died between `run.json` and its first journal line, before or after the ledger confirmation) journals `run-started` with `recovered: true` and the recorded `started_at`, whatever that open's confirmation finds (a damaged record or a moved directory included), so a run that has spent its activation always has a journal record of when it started and under which binding. A record that cannot be read is a use, never the absence of one; an unwritable ledger refuses `activation-ledger-unwritable` and creates no run. Nothing raised while marking a failed creation `aborted` replaces the creation's own error (it is attached as a note, and the record stays `pending`); a record that was not marked adds a note worded for why (only `FileNotFoundError` or `NotADirectoryError` from `os.stat` mean `run.json` is absent): `run.json` exists (`save_run` raised after the replace): reopen the same run, the next open confirms the record, do not re-issue; the ledger could not be written or `run.json` could not be examined: the record stays `pending` and a retry refuses `activation-used`; the record is missing, unreadable, no longer `pending` or names another run: it was left as it is, and the note says what a retry meets. `run.json` is examined first and whatever the record turns out to be: when it exists, every one of these notes keeps its reason, says "run.json exists: reopen the same run" and says what that reopen does with the record, and none promises a retry that writes a new record or refuses `activation-used` (a retry reopens the run that exists and creates nothing). When whether `run.json` exists could not be examined, the note says so and gives both: what a reopen does if it exists, and the retry advice if it does not. The `abort_cause` copied into the record and its `attempts` is capped at 500 characters. The tool never removes a record. Like the activation itself this is a trusted-machine control, not authentication: whoever can write to the machine can remove a record.
- `reserve` and every advancing operation (`record-head`, `run-checks`, `authorize-review`, `authorize-repair`, `record-review`, `propose-evidence`, `rebase-revisions`, the advancing replays of `resume`) require the same activation to still be current; `rebase-revisions` also refuses on a stopped run. Expiry is a stop like the wall clock: advancement refuses `activation-expired`, a late receipt binds for cleanup only, pending advancing intents are abandoned on resume. A file that is merely **not presented** on a healthy run is not a stop. `bind-receipt` refuses `activation-required` and changes nothing of the story or the budgets (the gate may still record that observation's time or a stop in `run.json`); a receipt for an authorization that was already **revoked** is cleanup and still binds for cleanup only, and `--for-cleanup --reason "…"` binds a launched task for cleanup only when the file is lost for good (`cleanup-requested`, journaled with the reason, which is required, `reason-required`; the slot is spent, no work is authorized, `cancel` / `block` then take its terminal evidence); it is refused while the run's current activation is presented (`cleanup-not-needed`: the task binds for work then, and a stray flag cannot end a healthy run). `resume` replays the owed cleanups, then **defers** its advancing part: nothing is reconciled, replayed, verified against GitHub, saved or abandoned; each deferred step is journaled once (`reconciliation-deferred`, `resume-advancing-deferred`, never `reconciliation-withheld`) and the call exits 3 with the activation's code, `"deferred": true` and the deferred `ops`, so a script never reads it as a completed resume. On an active story this holds even when the skipped revision check is all that was deferred (`ops: ["revisions"]`, journaled once as `resume-revisions-unverified`): the check waits for the file too. The next `resume` with the file completes it. A recorded `clock-regression` stop the owner can still clear (the run's one clear not spent, the run not cancelled, and the later of the clock and the run's high-water mark still at or before the recorded `expires_at`: past it no clear can succeed: the clear refuses `activation-expired` by the same rule) is treated the same way while no other durable cause applies (policy drift, the wall clock judged on the high-water mark): `resume` defers with code `clock-regression` and abandons nothing, and `bind-receipt` refuses a work bind with `clock-regression` and binds nothing (`--for-cleanup` still binds for cleanup); after the clear the deferred steps and the bind complete. Once the clear is spent, or another durable cause applies, the stop has the cleanup-only consequences below. `reconcile-retained-execution` refuses `run-not-stopped`; under a clock stop the owner can still clear it reconciles a revoked authorization (cleanup, as on any stopped run) and refuses a pending one with `clock-regression`, reconciling nothing (clear the stop or cancel the run: after the clear the pending repair binds for work); a repeat of a reconciliation already finished (from a revoked or a pending authorization) is answered as already reconciled when the evidence is identical and refused as conflicting otherwise. On a live run the clock may read behind the run's high-water mark: far behind under a recorded `clock-regression` stop, clearable or not, and up to the 5-minute tolerance behind after the stop is cleared or with no stop at all. So every state stamp the coordinator writes on a live run is the later of the clock and that mark, whether or not a stop is recorded and whichever operation writes it: `task_history[].at` (`record-task-terminal`, `cancel`, `block`), `blocked.at`, `bound_at` and `claim.claimed_at` of a bind (for work or for cleanup), `revoked_at` and `resolved_at` of an authorization, an intent's `created_at` and `completed_at`, the stamps of the advancing operations (`issued_at`, `claim.reserved_at`, `checks[].at`, `reviews[].at`, `proposal.at`), and the reconciliation's `bound_at`, `reconciliation.at`, `task_history` entry and backup name; one story therefore never holds a floored entry followed by an earlier one, across a clear included. A run with no later observation has the validated creation moment (`validated_at`) as its mark; a fixture run has no mark. One stamp is an exception: a story's `updated_at` is written by the store from the wall clock at every save and is not floored. The journal is not floored either: a line's `at` is the wall clock as it was read, the record of what the clock said, and the journal is ordered by `seq`, never by `at`. An authorization whose `issued_at` was floored keeps what the clock read as `issued_observed_at`, and the reconciliation's check that the run started at or after its authorization was issued (`run-precedes-authorization`) compares with that reading: the task starts on the real clock, which may still read earlier than the mark. The `run-precedes-authorization` refusal reports `started_at`, `issued_at` as recorded and `compared_with` naming the field that was compared, plus `issued_observed_at` when the authorization has one. `reconciliation.observed_at` keeps what the clock read; it is recorded under a clock stop, and without one only when `reconciliation.at` was floored; when the two differ the backup name also carries the real observation (`-obs<time>`), so a retry after a failed save does not meet `backup-exists` for as long as the clock stays behind. Only a cancelled run, a recorded stop (`activation-expired` / `clock-regression`), policy drift or an exceeded wall clock has the cleanup-only consequences; a recorded stop is reported ahead of a wall clock that ran out at the same moment.
- A recorded `clock-regression` stop (a host clock that stepped back more than 5 minutes behind an earlier observation, as WSL2 does after sleep) is meant to be cleared only by the owner: `clear-clock-regression --clearance <file>` needs the run's activation presented and current **and** a clearance, a TOML file the owner writes for exactly that stop (`run_id`, `activation_id`, `approver` and `stop_observed_at` copied from `status`, plus `reason`; exactly these keys). A clearance names one stop, so it cannot be written in advance or reused. **Owner-only is a convention on the trusted machine, not a control:** every field of a clearance is readable by the unattended loop (`run.json`, `status`), so a process on this machine that decides to clear its own stop can write a valid one, and the tool cannot tell who wrote it (a GitHub comment would prove nothing either: the loop posts as the owner's account). What the tool does enforce is where a clearance is read from: one whose real path lies inside `--state-dir` or inside any git work tree (`--repo-root`'s, the checkout the tool runs from, and the work tree the clearance's own directory belongs to, which covers a delegated task's linked worktree) refuses `clearance-invalid`, and so does one under any directory that has a `.git` entry of any kind (a directory, or a gitfile, dangling ones included, such as a delegated worktree left behind after `git worktree prune`) and one for which git cannot answer (git missing, a timeout, dubious ownership or any answer other than the plain discovery failure `fatal: not a git repository (or any of the parent directories)`: a `not a git repository: <path>` from a dangling gitfile is not that answer; git runs in the C locale, without inherited `GIT_*` variables and with `GIT_DISCOVERY_ACROSS_FILESYSTEM=1`, so a mount point such as a tmpfs `/tmp` does not stop its walk; the rule never passes because git failed). A clearance path that cannot be read is reported as what it is: no such file, permission denied (an unsearchable directory, or a file this account cannot read), or not a regular file; `warning:` lines git prints before its answer (an unreadable config file) are ignored. The work-tree refusal is applied by the CLI (the coordinator itself checks only the state directory). Paths are compared by real path and without regard to case, since the checkout may sit on a case-insensitive mount (`/mnt/c` under WSL); on a case-sensitive file system this also refuses a directory that differs from the state directory or a work tree only by case, and the refusal says "inside, or inside a case variant of". Recommended location: a dedicated directory outside every git work tree and the state directory, such as `~/.local/state/owl-mast-clearances/`; if the home directory is itself a git work tree (a dotfiles repository), choose a directory outside it (git must answer "not a git repository" there). The check narrows a race, it does not close one: a directory swapped for a symlink after the check, or a hard link, is not detected. The clear refuses while the clock still reads more than the 5-minute tolerance behind the run's latest observation (wait until it has caught up; within the tolerance it proceeds), keeps the high-water mark and judges the wall clock on the later of the clock and that mark, so a clock still a few minutes behind never buys time (and time a forward-skewed clock ran ahead is spent, never refunded: **a forward skew larger than the remaining wall-clock budget ends the run**, the stop then has the cleanup-only consequences and there is nothing left to clear); it refuses on a cancelled run or after the wall clock, and works once per run (`clock-clear-exhausted`: a clock that regresses again is not trusted, cancel the run). The clear is journaled `activation-stop-clear-started` (naming the stop) before `run.json` is written and `activation-stop-cleared` after: a write that fails leaves the stop recorded and the same clear may be retried; a save that reports an error after `run.json` was replaced (the stop is gone on disk) is the clear it is: the command returns the normal clear result (`journal_seq`, `run`) plus `save_uncertain` and exits 0, and the `activation-stop-cleared` line carries `save_uncertain` (`journal_seq` is `null` when that line could not be written either); an interrupt (Ctrl-C, `SystemExit`) after the replace writes a best-effort `activation-stop-cleared` line with `interrupted` and propagates; the one clear is spent once a `cleared` line exists or a `clear-started` line names a stop other than the one recorded now. A stop is named by its unique `stop_id`, so a second stop observed at the same second as a cleared one is still another stop; older stops have none and are named by their `observed_at`, and a `clear-started` line without a `stop_id` names an older stop than one that has one. An `activation-expired` stop is never cleared. While a `clock-regression` stop is recorded, `status` reports `activation.clock_stop`: `clearable`, `clear_spent`, `high_water`, `expires_at`, `wait_until` (while the stop is clearable but the clock is still more than the tolerance behind the high-water mark: the time the clock must read before the clear can run; `null` otherwise, and always `null` on a stop that is not clearable, where waiting unlocks nothing), `presented_current`, `clear_requires` and, when it is not clearable, `reason` (the run is cancelled, the one clear is spent, a recorded time cannot be parsed, the later of the clock and the high-water mark is past `expires_at`: the reason prints that later time and says whether it is the clock or the mark, policy drift makes the activation not current, or the wall clock judged on the mark is spent). `clearable` says what the stop is (`false`: it has its durable, cleanup-only consequences), not that a clear run now would succeed: the clear also needs the run's activation presented and current. `presented_current` is whether the activation given to this `status` call is the run's and current at this observation, and on a clearable stop `clear_requires` names `--activation` and the problem while it is not (none presented: `activation-required`; presented but not current, such as not yet valid: its code and message; while `wait_until` is set the document was judged on a clock that is behind the mark, so `clear_requires` also says that it is judged on the present clock and will be judged again once the clock reaches `wait_until`: a "before `issued_at`" reported then may be the regressed clock, and waiting is what is needed); it is `null` when nothing more is required and on a stop that is not clearable. A missing `--activation` never turns `clearable` false. git answers under a 30-second timeout; a timeout names the directory examined and says that a hung mount above it (a network share, autofs, a stale drvfs mount) is the likely cause. The bound is per git call, not for the clear: each call is given 30 seconds, and a git that is killed and does not exit (a process in uninterruptible sleep on a hung mount ignores the kill) is waited for at most 5 seconds more, then that call is given up whether or not it exited; the work-tree rule makes up to three calls (the repository's, the tool's and the clearance's own directory), so git can hold the clear for up to three times 35 seconds. The bound does not cover the tool's own examination of the clearance path (its `stat`, the read and the walk over its ancestors for a `.git` entry), which has no timeout. Like the activation, a clearance is a reviewable, journaled approval on the trusted machine, not authentication.
- Cleanup of a run that was activated earlier (`cancel`, `block`, `record-task-terminal`, `record-no-launch`, `cancel-run`, `reconcile-retained-execution`, the cleanup part of `resume`) works after expiry and even without the file, on the strength of the recorded binding; it still needs the exact terminal evidence and never advances. The recorded binding is the complete record persisted at creation (document id and digest, approver, window, repository, policy digest, run id, `approved`, `validated_at`) and is re-validated strictly against the run on every operation; a partial, foreign or inconsistent record refuses `activation-binding-invalid` without replacing the run's obligations. The record is validated against the run selected by `--run-id`, never against identities read from the same file: a genuine `run.json` restored from another run directory refuses `run-identity-mismatch` everywhere (creation, cleanup, cancel-run, late receipts, replay, `status`, the public `Store` entrypoints) and is never rewritten. The record's temporal facts are validated at the same load boundary: `validated_at` must be present and inside the approval window, `last_observed_at` must be null or a strict UTC time and `activation_stop` null or exactly the supported stop record (`activation-expired` / `clock-regression`, observation time, message, operation, and the optional `stop_id`); anything else refuses `run-state-invalid` and is never read as the absence of a control or replaced by the current time. A *different* activation (another id or an edited file, which changes the digest) is refused for every operation, cleanup included; the file is re-read at every operation, so editing it under a running coordinator refuses too, and a malformed file refuses until `--activation` is omitted; a deleted file stops advancement and leaves cleanup. A changed policy is refused by the existing run binding. Retained run artifacts without `run.json` are never adopted by a new run (`run-metadata-missing`).
- Every operation decides from one clock observation taken after the store lock is held (window, durable stop, wall clock, the `status` report); it cannot report or refuse on an expiry it did not record. An observed expiry (or a clock that moved back more than five minutes past the last observed time) is recorded durably in `run.json`; after that the run does not advance, whatever the clock says after a restart (`activation-expired` / `clock-regression`; an `activation-expired` stop is final, a `clock-regression` stop the owner can still clear defers `resume` and refuses a work bind instead of abandoning anything, see above); cleanup, late receipts (cleanup only) and terminal evidence stay allowed and approvals and budgets are untouched. A recorded stop outranks a wall clock that ran out at the same moment. The wall clock is judged everywhere on the later of the clock and the run's high-water mark, so a clock still within the 5-minute tolerance behind the mark never gives a run back time it was already observed to have used. `status` runs under the same locked gate as every other consumer: it reloads and validates the run, re-reads the source and records an observed expiry or clock regression durably before reporting it, so a stop first seen by `status` is as durable as one seen by `record-head`; a valid recorded binding without the file still reports, a changed or malformed source refuses. `status --read-only` takes no lock and writes nothing (a polling monitor never contends with worker operations and a single skewed sample never stops the run); it reports what this observation would record as `activation.would_stop` and leaves recording to the next locked operation; because it reads the run, story and journal files without the lock, a report taken while another operation writes may be torn across files, so the locked form is the coherent one. A recorded `clock-regression` stop is cleared with `clear-clock-regression --clearance` (described above; owner-only is a trusted-machine convention, not a control); an `activation-expired` stop is never cleared. A malformed `started_at` in `run.json` refuses `run-state-invalid` like the other time controls.
- **Trust model.** An activation is an engineering approval written by the trusted coordinator or owner on the trusted machine under the 2026-11-06 agreement. It is not a credential, not signed and not cryptographically verified: anyone who can write to the machine can write one. It adds an explicit, reviewable, journaled decision; it does not add authentication. Never commit an approved activation; the owner keeps the approved copy outside the repository for exactly one run.

Qualified safeguards are unchanged by the opt-in: stable ids and revisions, exact task/run/authorization/role/SHA success evidence on every consumer and replay, owner `Ready` and dependency closure, reservation before launch, no duplicate workers, the two-repair ceiling, budgets, checks before fresh review, intents and idempotency, strict cleanup and terminal evidence.

## Guarantees and limits (precise)

- **Revisions.** Admission, every proposal and every resume compare the recorded revisions (issue `updatedAt`, body hash, state, close reason, Project item `updatedAt`, Status) of the story's closure with a fresh read; any difference refuses. `rebase-revisions` is the only way to accept a change, and it is explicit, journaled and needs `--live` and a reason.
- **No owner field is written.** The only write is appending an issue comment. There is nothing to overwrite, so no compare-and-swap is needed or claimed.
- **Operation identity and payload.** Each effect is a write-ahead intent with a stable operation id and its complete comment body. Replays post exactly that body. Trust in markers is asymmetric and fails closed: only markers written by the identity the transport acts as (`gh api user`, or the GraphQL `viewer` for a GitHub App installation token) are ever adopted as our own effects or counted as duplicates of them, a `claim` from **any** author blocks admission and takes part in the claim race (`foreign-claim-counted`), and a `release`, `block` or `proposal` clears only a claim posted by the same author and run (`foreign-marker-ignored` otherwise), so a forged release cannot free a claim, a copied claim cannot be adopted or push ours into `conflict`, and two legitimate identities cannot admit one story. The price is that one stray or forged `claim` comment blocks admission until its author releases it, the owner runs `dismiss-claim` (a journaled `dismiss` marker by our identity naming the comment id, honoured by coordinators under this identity; it needs the run's current activation and an active run, never dismisses this run's own claim or a claim a run under this state directory still owns, and dismisses any other claim only when a run under this state directory proves it finished with the story or with `--force`, since a claim's age proves nothing), or the comment is deleted. Every marker also carries the run directory's instance nonce (`inst`), so two coordinators that share a run id on two machines or state directories are told apart; only a run created before the nonce existed (no `instance` in its `run.json`) reads a marker without `inst` as its own. The cross-story check costs one comment read per allowlisted story of the policy on every `reserve` (the allowlist is small by design) and sees only stories of this policy's allowlist. Every marker value is validated at render time so it reads back identically (`marker-value-invalid` otherwise). Zero markers ⇒ post, one ⇒ adopt, more than one ⇒ `conflict`, on first execution and on resume alike. After its claim lands, `reserve` reads the claims again, on this story and on every other allowlisted story: the earliest claim wins (a foreign claim from its creation, ours from its last edit, then comment id; one more read before cancelling, taken only on visible releases) and a later claimant cancels itself in the same operation, posts its release and refuses `claim-race-lost`, or `claim-active-elsewhere` when the earlier claim is on another allowlisted story; its story slot and task authorization stay spent (an issued slot is spent), so under `max_stories_per_run = 1` the run then admits nothing more and the next attempt needs a new run id. An intent's completion and the phase it carries (`reserved`, `proposed`) persist in one write; a completed intent found without its transition is reconciled on resume without posting. Advancing replays (claim, proposal) run only for an active story in a run that is neither cancelled nor past its wall clock and re-verify their preconditions (for a proposal: phase `review-approved`, approved and head SHA equal to the intent's SHA, no active task, then revisions, worktree and PR) before posting; otherwise the intent is abandoned and nothing is posted. A completed intent found without its transition is reconciled only behind the same gates, including the fresh evidence reads; otherwise its effect stays recorded, is never reposted and the phase is not advanced (or moves exactly as a fresh attempt would move it: invalidated, regression recorded). Terminal phases persist together with their cleanup intent and the abandonment of every pending advancing intent, so a crash cannot strand ownership or replay an abandoned effect; a reservation whose revisions changed before its checkpoint is cancelled in the same write as the release it owes (when its claim comment landed: one or many markers; zero ⇒ nothing owed), and a failed release post is replayed by the next resume.
- **Task capacity and ownership.** Every delegated task is authorized durably before its launch (`reserve`, `authorize-review`, `authorize-repair`); an issued authorization counts against `max_delegated_tasks` whether or not it is bound (a `not-launched` resolution refunds nothing), `bind-receipt` consumes exactly the authorization named by `--authorization` and accepts only a task id never bound anywhere in the run (receipts of both roles, active tasks, consumed authorizations and terminal history of every story, kept through cancellation and blocking), repair rounds are counted at authorization, and all three budgets are derived from the story files under the lock (corrupted or stale `run.json` counters cannot bypass them). After the wall clock, or once the run is cancelled, no authorization is returned or issued and no advancing operation runs; a receipt for an earlier authorization binds for cleanup only (slot spent, id bound, task owned, phase unchanged). An authorization that was issued but never bound is an obligation: cancelling or blocking the story, invalidating the evidence or stopping the run revokes it (no work can be bound to it) but does not resolve it; the claim, the concurrency slot and the story stay owned, no replacement is issued, and only the exact receipt followed by terminal evidence, or the coordinator's `record-no-launch` attestation for that id, resolves it (`cancel-run` lists such stories as awaiting). The active task (id, role, authorization) is independent of the phase: HEAD recording (same or new SHA), verdicts, evidence invalidation, cancellation of the run and the expiry never release it; only terminal evidence for exactly that task does. A story state file with another schema is refused, never reinterpreted.
- **Serialization and binding.** One non-blocking `fcntl` lock per state directory covers admission, budgets and effects; a second coordinator (same or another process) gets `store-busy`. A run is bound to its repository, policy digest and environment. Budgets are per run id; `reserve` refuses `run-concurrent` while another run under the same state directory still owns a story, and `claim-active-elsewhere` while any other coordinator (any state directory, any machine, any identity) holds an active claim marker on any other allowlisted story, so the single-active-story rule is enforced on GitHub, not only locally. The policy digest is the sha256 of the canonical parsed policy (every field, sorted keys), so a comment or whitespace edit is the same policy and strands nothing, while a change to what is dispatched, with which targets, budgets, checks or probes is **policy drift**: journaled once (`policy-drift`), reported by `status`, a run stop for admission and advancement while cleanup proceeds on the recorded binding; a late receipt under drift is validated against the targets recorded when the run was created and binds for cleanup only; a run created before the canonical digest existed is recognized by the raw-bytes digest of exactly its policy bytes and is never rewritten. The activation binds the canonical digest: a new live run is created only under an activation naming it, while a run that already exists bound to the raw-bytes digest of exactly these bytes still takes the activation that names that digest (`check-activation` reads the run's bound digest from the state directory when `--run-id` names an existing run, and looks no run up without `--run-id`; a raw-digest activation for a run that does not exist is `activation-mismatch`). Project reads resolve the owner as a user or an organization; an item from another repository in the same Project (compared case-insensitively) is dropped and counted in the snapshot (`dropped_items`), a Project none of whose items links this repository refuses `project-items-foreign`, and two items for one issue refuse `ambiguous-project-item`; a label, field-value or option connection larger than one page is paginated to the end (a page without a cursor or an endless connection refuses), so one over-large issue never refuses the whole snapshot. GitHub's primary and secondary rate limits (HTTP 403/429 with a rate-limit message) are outages, never permission verdicts. The policy loader coerces nothing: booleans, integers with bounds (timeouts at least 1; `max_wall_clock_minutes` at most 10080, `checks.timeout_minutes` at most 1440, `probes.timeout_seconds` at most 86400), arrays of strings and tables are checked by type, so `"false"` never enables an epic. A story file that is not readable JSON, not a record, or a record whose phase or field types are not a story's refuses `state-corrupt` for every operation that reads it, while `status` and `cancel-run` read tolerantly (the overview names the unreadable file, the release of every readable story proceeds and the unreadable one is reported with its code); a torn journal line is terminated and reported as `journal-torn-line`; atomic writes fsync their directory and every directory they create is fsynced in its parent (the journal's first line included); a git that cannot answer at an evidence gate refuses `worktree-unreadable` without invalidating anything. The CLI never prints argparse usage on a malformed call: it is one JSON document with `input-invalid` and exit 3 (`--help` still exits 0), so exit 2 means exactly a negative result (`plan`/`check-activation` with problems, a non-idempotent `probe-write`).
- **Fail closed.** Unknown declarations, unknown close reasons, duplicate stable ids, missing Project items, inconsistent issue state, permission denial, outage, malformed or truncated review pages, parse failures, binding, schema and worktree mismatches refuse without advancing.
- **Live transport.** Fixture tests cover the fault matrix and the production transport parser with realistic responses. Live GitHub evidence is read-only plus one idempotent comment on #106. Live T3 evidence is this tool's own delegated-task receipt. No product story has been dispatched and none can be without an owner-approved, run-bound activation (the opt-in below).

## Permissions and secrets

This tool needs: Issues read/write (comments), Pull requests read, Contents read, Metadata read, and **Project read**. Pushing implementation branches and opening PRs is the implementer identity's privilege, assessed separately. No classic token satisfies the Project read-only boundary: posting comments needs classic `repo`, and GitHub's scope documentation states that `repo` "also grants the ability to manage projects owned by users"; scopes are a union, so `repo` + `read:project` is **not** read-only on the Project and that candidate is disqualified. `check-permissions` reports `basic_access` (the identity can act) and always reports `bounded: false` and `unattended_activation_allowed: false`, because scope names, push and a non-admin flag never prove a bounded credential; `denial_tested` and `resource_scope_verified` stay false until a qualification this probe does not perform. That qualification may probe a read-only denial against the live repository, but a **Project-write denial only against a separately authorized disposable qualification resource** (never Project 2 or a backlog issue), with an unexpected success recorded as disqualification of the candidate. On 2026-11-06 the operator token has basic access, is admin, can update the Project, and carries `admin:public_key`, `gist`, `read:org`, `workflow`. Candidate credentials and their open questions are in the [permissions document](https://github.com/gabrianoo/owl-mast/issues/106#issuecomment-6838328214) on #106; none has been provisioned or tested, and no denial probe has been run. Tokens never enter policy, state or logs; a bounded identity's `GH_TOKEN` would be obtained through T3 `request_secret` with file delivery and exported for the command only.
