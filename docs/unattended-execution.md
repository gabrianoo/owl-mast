# Unattended execution foundation (ENG-01)

`automation/unattended` is the smallest supported bridge between the GitHub backlog that owns engineering progress ([tracking contract](engineering-tracking.md)) and a T3 coordinator that dispatches story work. It is engineering automation, tracked in [ENG-01 (#106)](https://github.com/gabrianoo/owl-mast/issues/106), outside the OM product numbering. It does not run on its own: a T3 coordinator thread calls it between `delegate_task` turns. There is no loop, schedule or daemon, and the installed `bmad-loop` CLI is not used.

**Operating agreement (owner-accepted 2026-11-06, supersedes the strict prerequisites below as explicitly stated).** The owner accepted a trusted-machine agreement (`_bmad-output/implementation-artifacts/spec-eng-01-trusted-operation.md`): the operator's development machine is trusted (worktrees isolate files, not host credentials); budgets are coordinator-enforced best effort (stop dispatch and request cancellation on expiry; a coordinator failure can leave a worker running); restricted credentials are used where practical and broad ones are disclosed as broad, never certified bounded; Project Status and acceptance stay manual owner actions and machine comments are evidence proposals. It supersedes the earlier requirement that hard child bounds, exhaustive credential-denial qualification and automated Project Status synchronization must precede all unattended work. It does **not** assert those guarantees exist, and accepting the risk is **not** activation: every real-transport state command stays refused and the default allowlist stays empty for this effort. Earlier results below are historical and keep their original labels.

## What GitHub owns and who writes what

| Fact | Where | Writer | Meaning |
| --- | --- | --- | --- |
| Stable ID, parent epic, `Depends on`, `Epic prerequisites`, tasks | Issue body | Owner through Git-revised specs | Specification. Read with a strict grammar (`None` or a comma-separated list of ids); anything else is unknown and blocks dispatch. |
| Project Status (`Backlog`, `Ready`, `In progress`, `In review`, `Blocked`, `Done`) | Project 2 Status field | **Owner only** | `Ready` = owner acceptance; `Done` = accepted completion. GitHub offers no compare-and-swap, so the machine never writes this field. It reads it for eligibility and treats any change as a stale revision. |
| Machine checkpoints | Issue comments `<!-- unattended kind=… run=… story=… op=… -->` | Machine, append-only | `claim`, `release`, `block`, `proposal`, `probe`. One comment per operation identity; a duplicate is a conflict. |
| Task checkboxes | Issue body | Owner | The `proposal` comment lists tasks with the exact commit; the owner ticks them. |
| Issue open/closed | Issue | Owner | Closing as completed is acceptance; any other or unknown close reason is not. |
| CI pass, review approval, merge, deployment | PR checks, PR reviews, merge, release | GitHub / reviewer / owner | Read, never written; each stays a distinct fact. |

Project Status synchronization is **not implemented**: there is no safe equivalent on GitHub's API. The owner moves Status by reading the machine's comments.

Dispatch is possible only when all of these hold: the story is in the policy allowlist; its epic is not E17/E19 (unless explicitly included); its Project item exists with a matching Stable ID; both declarations parse; Status is `Ready`; every `Depends on` story and every story of a prerequisite epic is `Done` **and** closed with the explicit reason `COMPLETED`. A story in `contract_design_exceptions` may run its designated design portion before prerequisites, flagged `dispatchable-contract-design-only`. Anything unknown fails closed.

## Commands

All commands print one JSON document. Global flags go before the command.

```sh
python3 -m automation.unattended verify-mapping            # 19/85/340 and relationships against live GitHub
python3 -m automation.unattended --policy automation/examples/first-run-om-01-02.toml plan   # dry run, writes nothing
python3 -m automation.unattended check-permissions         # basic_access observation; bounded and activation are never granted by this probe (exit 2)
python3 -m automation.unattended probe                     # environment probes from policy
python3 -m unittest discover -s automation/tests -t .      # qualification suite (fixtures)
```

State commands need `--run-id`; anything that can reach a GitHub write also needs `--live` (`reserve`, `authorize-repair`, `propose-evidence`, `block`, `cancel`, `cancel-run`, `resume`, `rebase-revisions`, `probe-write`). On the real transport a new run and every advancing operation need `--activation <file>` naming a current activation authorization; without one they refuse `activation-required` before any GitHub call. Cleanup and `status` of a run that was activated earlier work on the run's validated recorded binding without the file (see below); a partial or foreign recorded binding refuses `activation-binding-invalid` and nothing is released. State lives under `.unattended-runs/<run-id>/` (gitignored: `run.json` with its environment binding, `journal.jsonl`, `stories/<ID>.json`); a store-wide `fcntl` lock serializes every operation across processes. Budgets are derived from the story files under that lock; `run.json` counters are a cache for `status`.

```sh
U="python3 -m automation.unattended --live --run-id <run-id>"
E='{"taskId": "<id>", "status": "result_available"}'            # terminal evidence from task_status (or a terminal task_cancel result) for the ACTIVE task
$U reserve OM-01.02 --baseline <sha>                           # admission + implementer authorization BEFORE delegate_task (refused on the real transport unless --activation is current)
$U bind-receipt OM-01.02 --receipt receipt.json --worktree <path> --branch <branch> --authorization <id>   # consumes exactly that authorization (its id came from reserve) after delegate_task returned the task id
$U record-head OM-01.02 --sha <sha> --task-evidence "$E"       # the implementer task is terminal; its exact commit is recorded
$U run-checks OM-01.02 --sha <sha> --cwd <worktree>           # full configured set on the exact clean HEAD; the only check evidence
$U authorize-review OM-01.02 --sha <sha>                      # worktree re-read; reviewer authorization BEFORE delegate_task
$U bind-receipt OM-01.02 --receipt reviewer-receipt.json --authorization <id>   # consumes it; the reviewer is now the active task; the receipt carries the authorized SHA
$U record-review OM-01.02 --sha <sha> --verdict approved|changes-requested --report <ref> --task-evidence "$E"
$U authorize-repair OM-01.02                                  # budgeted; required after any failure; at most two rounds, then blocked; then bind-receipt
$U record-task-terminal OM-01.02 --task-evidence "$E"         # release the active task without recording anything else (e.g. after an invalidation)
N='{"authorization": "<id>", "reason": "delegate_task was never called"}'   # no-launch attestation for an UNRESOLVED authorization (no receipt will ever come)
$U record-no-launch OM-01.02 --no-launch "$N"                 # resolve it; slot stays counted; nothing else changes
$U propose-evidence OM-01.02 --sha <sha> --pr <n> --task OM-01.02-T1 --summary "…"
$U cancel|block OM-01.02 --reason "…" [--task-evidence "$E"] [--no-launch "$N"]   # evidence required while a task is active; attestation (or the late receipt) required while an authorization is unresolved
$U cancel-run --reason "…" [--task-evidence '{"OM-01.02": {...}}'] [--no-launch '{"OM-01.02": {...}}'];  $U resume OM-01.02;  $U rebase-revisions OM-01.02 --reason "…";  $U status
```

## Coordinator protocol (T3) and what is and is not established

1. `verify-mapping` and `probe` must pass; `check-permissions` must report `basic_access` (it never reports a bounded credential, see below).
2. `plan` decides eligibility from a fresh snapshot; a stable id carried by more than one issue (in the plan snapshot or the fresh read) is `ambiguous-identity` and admits nothing. `reserve` re-reads every revision the decision depends on (story, parent epic, dependency closure, Project items) under the store lock, issues the implementer **task authorization** (counted against `max_delegated_tasks` from that moment, bound or not) and posts the claim marker **before** any task exists; an exhausted task budget refuses here, before any launch.
3. `delegate_task` with `isolation: "worktree"`, `role: "implementation"`, target `claudeAgent` / `claude-fable-5-1` / `options {effort: "high"}`; `bind-receipt --authorization <id>` validates the receipt (exact model and effort, a task id never bound anywhere in the run: any story, any role, terminal or not), the worktree identity, consumes **exactly the named authorization** (a wrong or stale id is refused; a reviewer receipt records the SHA that authorization was issued for, never the current head) and makes the task the story's **active task**. One active story per run and one active task per story, enforced under the lock; a story is admitted at most once per run (no reclaim); an authorization binds once. **An issued authorization is an ownership obligation until it is resolved**: the tool cannot see whether `delegate_task` was called, so until the exact receipt arrives (and that task's terminal evidence follows) or the coordinator attests `record-no-launch` for that id, the story stays owned — `cancel`/`block`/`cancel-run` refuse with `authorization-unresolved` (and revoke the authorization so that no work is ever bound to it), no release is posted, no other story is admitted and no replacement authorization is issued. If the run stopped after the authorization was issued (cancelled, or past `max_wall_clock_minutes`), or the authorization was revoked, the receipt still binds but **for cleanup only**: the slot stays spent, the id stays bound, the task is owned until its terminal evidence, the phase does not advance and the command refuses with `bound_for_cleanup`, so the coordinator cancels the task instead of working it. A reservation that never returned (`claim-incomplete`) is the one case the state itself proves unlaunched.
4. `record-head` with the exact commit and the implementer's terminal evidence (`task_status` `workState: result_available` or a terminal `task_cancel` result), then `run-checks` in the claimed worktree. Checks fail ⇒ `authorize-repair` (round 1 or 2, counted at authorization, then `bind-receipt` of the new implementer task) or `block`; `record-head` after a failure without an authorized and bound repair is refused.
5. `authorize-review` only after the full configured check set passed at that commit, the worktree still reads that commit and is clean, and no task is active; then `delegate_task` for a fresh `codex` / `gpt-6-astra` / `options {reasoningEffort: "high"}` reviewer and `bind-receipt`. `record-review` needs the reviewer's terminal evidence, binds the verdict to the commit and re-reads the worktree; any unreported change or a new commit invalidates check and review evidence and abandons a pending proposal, but never releases the active task; a pending review authorization is revoked, not abandoned, and its reviewer (if launched) must be bound and terminated, or attested unlaunched, before checks run or a new review is authorized for the new commit.
6. `propose-evidence` after approval: phase `review-approved`, approved and head SHA equal to the proposed commit, no active task, revisions unchanged, worktree re-read, PR head equals the approved commit, PR open and unmerged, every review page read, no reviewer with an outstanding `CHANGES_REQUESTED`, CI not failing; posts the persisted proposal body and the `proposed` phase in one write. Merge, `Done`, Status and closing remain owner actions.
7. Terminal acknowledgement is not result evidence, and success must be identified and linked: only a `completed`/`result_available` terminal record of exactly the bound `(taskId, runId)`, recorded in the relevant role for exactly the authorization the coordinator selected (the latest consumed implementer authorization; for the reviewer, the one issued for exactly that SHA), is successful; `interrupted` (the real transport's status for a cancelled run), `failed` and `cancelled` release ownership but never advance. One common gate runs on **every** advancing consumer of recorded evidence — `record-head` (also its same-SHA no-op), `run-checks`, `authorize-review`, `authorize-repair`, `record-review`, `propose-evidence` and both `resume` proposal paths (a pending replay and a completed proposal whose transition did not persist) — whatever path led there: direct evidence, `record-task-terminal` then a reload, an upgrade from state an older coordinator wrote, or a restart. A head, check result, approval or posted proposal recorded by an older coordinator over an unsuccessful execution is history, never evidence: on `resume` a pending proposal is abandoned (nothing posted) and a landed one keeps its comment without advancing (`reconciliation-withheld`); `cancel`/`block` remain the way out. An absent run identity on the authorization or the record (`run-identity-missing`), a record for another run or none at all (`no-successful-execution`), a record whose role or `authorization` does not match the selected authorization (`conflicting-evidence`) and an unsuccessful or contradictory outcome (`worker-interrupted`/`worker-unsuccessful`) all refuse; task-only completion is never an identified execution. Legacy history without the `successful` flag is read from its status, and a flag that contradicts its status is unsuccessful; nothing is migrated or rewritten. `bind-receipt` and `reconcile-retained-execution` are ownership and cleanup, not evidence, and are not gated; the regression fixtures under `automation/tests/fixtures/legacy-bb4c3ee/` are states the pre-repair coordinator produced through its own commands (`automation/tests/legacy_baseline.py`).
8. Ownership is released only with terminal evidence for exactly the active task: `cancel`/`block`/`record-task-terminal` need `{taskId, status}` matching it (implementer evidence never releases a reviewer); an unresolved authorization is released only by its exact receipt plus that task's terminal evidence or by `record-no-launch` naming it (the coordinator's attestation, trusted like a receipt); `cancel-run` marks the run cancelled, releases the stories that owe nothing and reports the rest (active task or unresolved authorization); a cancelled run, or one past its wall clock, refuses every advancing operation (no authorization is returned or issued; the pending slot stays spent) while still accepting terminal evidence and cleanup. The wall clock is a local expiry of this tool's authorizations; it does not stop a launched child. Cancelling or blocking a story abandons its pending advancing intents in the same write as the terminal phase. `resume` checks the worktree identity first, replays cleanups, then reconciles a completed intent whose transition did not persist only where a fresh attempt would be allowed (run neither cancelled nor past its wall clock; a claim only with unchanged revisions, otherwise the story is cancelled together with the release it owes; a proposal only with phase `review-approved`, exact-SHA approval and head, no active task or unresolved authorization, and only after fresh revisions with unique identities, the re-read worktree and the PR re-verify, with the same consequences as a fresh proposal), otherwise keeps the effect as history without advancing or reposting (`cancel`/`cancel-run` finish the story); then it abandons advancing intents of a terminal story or a stopped run, re-validates the remaining ones (claim: revisions, changed ⇒ cancelled with its release when the claim comment landed; proposal: current phase and exact-SHA approval, revisions, worktree, PR) before posting their persisted payload, then refuses on changed revisions.

**What the installed T3 tools support and what remains.** The tool metadata supports the protocol above: authorization happens under the local lock before `delegate_task`; the receipt is bound afterwards; `task_status` reports `workState` (`working`, `waiting_for_children`, `result_available`) and the final summary; `task_cancel` stops the task's running and queued turns and its delegates and, per the coordinator's inspection of the tool metadata, reports `cancel_requested` or a terminal state. Under the accepted agreement the remaining facts are residual risks, not prerequisites: there is no hard deadline or resource bound on a delegated child (`timeoutMs` limits the wait in `mode: wait` only), no credential confinement (the child runs with the machine's credentials), and launches are invisible to the tool (it bounds what can be bound; receipts, terminal evidence and no-launch attestations are the coordinator's reports). No upstream T3 work is required for this agreement. What is still required before any activation is the engineering-only lifecycle smoke with real receipts (`automation/tests/lifecycle_smoke.py`, run by the coordinator, never by a unit test), its published evidence and a fresh independent review; until then nothing is activated: the unconditional `live-execution-disabled` refusal has been replaced by the explicit, run-bound activation authorization described [below](#activation-authorization-explicit-opt-in), and the shipped policy and committed candidate still dispatch nothing.

## Lifecycle smoke helper (manual steps, synthetic state)

`python3 -m automation.tests.lifecycle_smoke --dir <fresh dir> <operation>` performs one operation per invocation against a JSON-persisted fixture transport (no network, fixture environment, fixture-only story `OM-99.01` under epic `E99`) and the coordinator's own run store: `prepare` (synthetic backlog, policy allowing only `OM-99.01`, optional synthetic git worktree, reservation), `bind` (receipt to the exact authorization, `--source real|fixture`), `head`, `check` (the configured commands on the exact clean HEAD), `authorize-review`, `bind` (reviewer), `review`, `cancel`, `terminal`, `restart` (fresh process reloads persisted transport and state and resumes), `status`. It never fabricates receipts or evidence: whatever the coordinator supplies is recorded verbatim with its declared source, so a published smoke counts as real only when the receipts and terminal evidence came from real `delegate_task`/`task_status`/`task_cancel` results and the review from a fresh GPT-6 Astra High task. Unit tests drive it with `--source fixture` and are labelled fixtures.

## Execution identity: (taskId, runId) pairs and the retained owner (third repair, 2026-11-07)

A resumed T3 owner keeps its task id and gets a new run id; `t3_thread_send` returns the run id only. Executions are therefore `(taskId, runId)` pairs: `taskId` stays the `task_cancel` handle and is never replaced by a run id; `runId` identifies the execution a receipt or terminal evidence is about. Canonical coordinator reports:

- Receipt: `{"taskId", "runId", "providerInstanceId", "model", "options", "isolation"}`. A fresh `delegate_task` receipt may carry the run as `childRunId` instead. A receipt naming two different runs is ambiguous and refused, except for a retained owner being re-run, where `runId` is the current run and `childRunId` the stale first run.
- Terminal evidence: normalized `{"taskId", "runId", "status"}`, or `task_status`-shaped `{"taskId", "workState": "result_available", "hasPendingChildRuns": false, "latestTerminalRunId", "latestTerminalStatus"}`. Only the latest terminal fields identify the terminal run; `childRunId`, `status` and `summary` are stale first-run fields and are ignored. Live or pending child work, a missing terminal run, `cancel_requested` or a run that differs from the bound execution refuses and keeps ownership.
- Retained owner: only the story's own implementer task (the one bound to its implementation authorization) may be bound again, only for a repair authorization, only with a run never bound anywhere in the run, and only after its previous execution is terminal. Reviewer tasks are never reused: a new run on an old reviewer task is not a fresh review. Legacy records without a run id are never completed by inference; a legacy active task without a run id stays owned and the missing fact is reported.

`reconcile-retained-execution` is the audited cleanup for the historical case (a revoked repair authorization whose task ran as a new run of the retained owner but was never bound): it needs the exact authorization id, a receipt of the retained owner naming that run with the dispatch record of the resumed run (`{"dispatch": {"runId", "messageId"}}`), `startedAt` at or after the authorization's `issued_at` (an older run of the same task can never settle a later authorization), matching terminal evidence, a reason and the provenance of the evidence, and the bound worktree/branch. It is cleanup for a stopped run only (cancelled or past its wall clock), reloads the run under the lock, resolves only that obligation (status `consumed`, cleanup only), writes a backup of the story file first, re-authorizes nothing, approves nothing, admits nothing, keeps the run cancelled and the budgets spent, and creates no no-launch attestation. Identical evidence (status, dispatch, timestamps, target, worktree) is idempotent; any difference is conflicting evidence and refuses. An ordinary `bind-receipt` of a retained owner whose history is legacy task-only is refused (`run-identity-missing`): the missing run identity is never guessed. The smoke helper exposes it as `reconcile` (with `--run-id` for a historical copy); the parent exercises it on an isolated copy before touching any historical state. Recovery commands:

```sh

  --authorization eng01-trusted-20261106:OM-99.01:3 --receipt receipt.json --task-evidence evidence.json \
  --reason "repair run ordinal5 completed under the retained owner" --provenance "original coordinator snapshot, user-supplied" --source real
#   receipt.json: taskId/runId (ordinal5)/provider/model/options/isolation from the snapshot, plus "dispatch" from repair-dispatch.json and startedAt/completedAt

```

## Activation authorization (explicit opt-in)

The unconditional `live-execution-disabled` refusal is replaced by an explicit, run-bound **activation authorization**: a TOML file (`automation/examples/activation-om-01-02.candidate.toml` is the committed, **unapproved** candidate) passed as `--activation <file>`. Nothing is activated by default:

- Without `--activation`, no live run is created and every admitting or advancing state command on the real transport refuses `activation-required` before any GitHub call; on a run that was never activated this includes `status` and cleanup. The shipped `automation/policy.toml` keeps `allow = []`. The one exception is deliberate and listed below: cleanup and `status` of a run that **was** activated earlier work on its validated recorded binding without the file.
- The committed candidate has `approved = false`, a placeholder run id, a zero policy digest and an expired window; copied as-is it refuses (`activation-unapproved`, `activation-mismatch`, `activation-expired`). `check-activation` reports exactly why without touching state or GitHub.
- An activation is **current** only when all of these hold at the moment of the operation: `approved = true`; `binding` names this repository, the sha256 of the exact policy file in use, `environment = "live"` and the exact `--run-id`; `scope.stories` equals the policy allowlist; `targets` and `budgets` equal the policy's (any model, option, isolation or budget drift refuses); `issued_at <= now <= expires_at` with a window of at most 24 hours; `evidence` cites the published lifecycle smoke and fresh review.
- A live run is created only under a current activation and records its binding (id, file digest, approver, window) in `run.json`. `reserve` and every advancing operation (`record-head`, `run-checks`, `authorize-review`, `authorize-repair`, `record-review`, `propose-evidence`, `rebase-revisions`, the advancing replays of `resume`) require the same activation to still be current. Expiry is a stop like the wall clock: advancement refuses `activation-expired`, a late receipt binds for cleanup only, pending advancing intents are abandoned on resume.
- Cleanup of a run that was activated earlier (`cancel`, `block`, `record-task-terminal`, `record-no-launch`, `cancel-run`, `reconcile-retained-execution`, the cleanup part of `resume`) works after expiry and even without the file, on the strength of the recorded binding; it still needs the exact terminal evidence and never advances. The recorded binding is the complete record persisted at creation (document id and digest, approver, window, repository, policy digest, run id, `approved`, `validated_at`) and is re-validated strictly against the run on every operation; a partial, foreign or inconsistent record refuses `activation-binding-invalid` without replacing the run's obligations. The record is validated against the run selected by `--run-id`, never against identities read from the same file: a genuine `run.json` restored from another run directory refuses `run-identity-mismatch` everywhere (creation, cleanup, cancel-run, late receipts, replay, `status`, the public `Store` entrypoints) and is never rewritten. The record's temporal facts are validated at the same load boundary: `validated_at` must be present and inside the approval window, `last_observed_at` must be null or a strict UTC time and `activation_stop` null or exactly the supported stop record (`activation-expired` / `clock-regression`, observation time, message, operation); anything else refuses `run-state-invalid` and is never read as the absence of a control or replaced by the current time. A *different* activation (another id or an edited file, which changes the digest) is refused for every operation, cleanup included; the file is re-read at every operation, so editing it under a running coordinator refuses too, and a malformed file refuses until `--activation` is omitted; a deleted file stops advancement and leaves cleanup. A changed policy is refused by the existing run binding. Retained run artifacts without `run.json` are never adopted by a new run (`run-metadata-missing`).
- An observed expiry (or a clock that moved back more than five minutes past the last observed time) is recorded durably in `run.json`; after that the run never advances again, whatever the clock says after a restart (`activation-expired` / `clock-regression`); cleanup, late receipts (cleanup only) and terminal evidence stay allowed and approvals and budgets are untouched. `status` runs under the same locked gate as every other consumer: it reloads and validates the run, re-reads the source and records an observed expiry or clock regression durably before reporting it, so a stop first seen by `status` is as durable as one seen by `record-head`; a valid recorded binding without the file still reports, a changed or malformed source refuses.
- **Trust model.** An activation is an engineering approval written by the trusted coordinator or owner on the trusted machine under the 2026-11-06 agreement. It is not a credential, not signed and not cryptographically verified: anyone who can write to the machine can write one. It adds an explicit, reviewable, journaled decision; it does not add authentication. Never commit an approved activation; the owner keeps the approved copy outside the repository for exactly one run.

```sh
python3 -m automation.unattended --policy automation/examples/first-run-om-01-02.toml --activation <private approved copy> --run-id <run> check-activation   # read-only: current or the exact problems
U="python3 -m automation.unattended --policy automation/examples/first-run-om-01-02.toml --activation <private approved copy> --live --run-id <run>"
```

Qualified safeguards are unchanged by the opt-in: stable ids and revisions, exact task/run/authorization/role/SHA success evidence on every consumer and replay, owner `Ready` and dependency closure, reservation before launch, no duplicate workers, the two-repair ceiling, budgets, checks before fresh review, intents and idempotency, strict cleanup and terminal evidence.

## Guarantees and limits (precise)

- **Revisions.** Admission, every proposal and every resume compare the recorded revisions (issue `updatedAt`, body hash, state, close reason, Project item `updatedAt`, Status) of the story's closure with a fresh read; any difference refuses. `rebase-revisions` is the only way to accept a change, and it is explicit, journaled and needs `--live` and a reason.
- **No owner field is written.** The only write is appending an issue comment. There is nothing to overwrite, so no compare-and-swap is needed or claimed.
- **Operation identity and payload.** Each effect is a write-ahead intent with a stable operation id and its complete comment body. Replays post exactly that body. Zero markers ⇒ post, one ⇒ adopt, more than one ⇒ `conflict`, on first execution and on resume alike. An intent's completion and the phase it carries (`reserved`, `proposed`) persist in one write; a completed intent found without its transition is reconciled on resume without posting. Advancing replays (claim, proposal) run only for an active story in a run that is neither cancelled nor past its wall clock and re-verify their preconditions (for a proposal: phase `review-approved`, approved and head SHA equal to the intent's SHA, no active task, then revisions, worktree and PR) before posting; otherwise the intent is abandoned and nothing is posted. A completed intent found without its transition is reconciled only behind the same gates, including the fresh evidence reads; otherwise its effect stays recorded, is never reposted and the phase is not advanced (or moves exactly as a fresh attempt would move it: invalidated, regression recorded). Terminal phases persist together with their cleanup intent and the abandonment of every pending advancing intent, so a crash cannot strand ownership or replay an abandoned effect; a reservation whose revisions changed before its checkpoint is cancelled in the same write as the release it owes (when its claim comment landed: one or many markers; zero ⇒ nothing owed), and a failed release post is replayed by the next resume.
- **Task capacity and ownership.** Every delegated task is authorized durably before its launch (`reserve`, `authorize-review`, `authorize-repair`); an issued authorization counts against `max_delegated_tasks` whether or not it is bound (a `not-launched` resolution refunds nothing), `bind-receipt` consumes exactly the authorization named by `--authorization` and accepts only a task id never bound anywhere in the run (receipts of both roles, active tasks, consumed authorizations and terminal history of every story, kept through cancellation and blocking), repair rounds are counted at authorization, and all three budgets are derived from the story files under the lock (corrupted or stale `run.json` counters cannot bypass them). After the wall clock, or once the run is cancelled, no authorization is returned or issued and no advancing operation runs; a receipt for an earlier authorization binds for cleanup only (slot spent, id bound, task owned, phase unchanged). An authorization that was issued but never bound is an obligation: cancelling or blocking the story, invalidating the evidence or stopping the run revokes it (no work can be bound to it) but does not resolve it; the claim, the concurrency slot and the story stay owned, no replacement is issued, and only the exact receipt followed by terminal evidence, or the coordinator's `record-no-launch` attestation for that id, resolves it (`cancel-run` lists such stories as awaiting). The active task (id, role, authorization) is independent of the phase: HEAD recording (same or new SHA), verdicts, evidence invalidation, cancellation of the run and the expiry never release it; only terminal evidence for exactly that task does. A story state file with another schema is refused, never reinterpreted.
- **Serialization and binding.** One non-blocking `fcntl` lock per state directory covers admission, budgets and effects; a second coordinator (same or another process) gets `store-busy`. A run is bound to its repository, policy digest and environment. Coordinators on other machines are detected through foreign claim markers, not excluded.
- **Fail closed.** Unknown declarations, unknown close reasons, duplicate stable ids, missing Project items, inconsistent issue state, permission denial, outage, malformed or truncated review pages, parse failures, binding, schema and worktree mismatches refuse without advancing.
- **Live transport.** Fixture tests cover the fault matrix and the production transport parser with realistic responses. Live GitHub evidence is read-only plus one idempotent comment on #106. Live T3 evidence is this tool's own delegated-task receipt. No product story has been dispatched and none can be without an owner-approved, run-bound activation (the opt-in below).

## Permissions and secrets

Pushing implementation branches and opening PRs is the implementer identity's privilege, assessed separately. No classic token satisfies the Project read-only boundary: posting comments needs classic `repo`, and GitHub's scope documentation states that `repo` "also grants the ability to manage projects owned by users"; scopes are a union, so `repo` + `read:project` is **not** read-only on the Project and that candidate is disqualified. `check-permissions` reports `basic_access` (the identity can act) and always reports `bounded: false` and `unattended_activation_allowed: false`, because scope names, push and a non-admin flag never prove a bounded credential; `denial_tested` and `resource_scope_verified` stay false until a qualification this probe does not perform.
