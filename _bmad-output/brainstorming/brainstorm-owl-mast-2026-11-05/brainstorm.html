    The pilot proposal

    1. Choose one project, one tracker, GitHub and one coding harness. Collect a baseline.
    2. Capture the work ID, context versions, runtime cost events, PR link, acceptance evidence and a proposed lesson.
    3. Produce a PR/ticket receipt. Reconcile the cost range and trace one shipped change through deployment.
    4. Let a second teammate retrieve a useful lesson in a later session. Record whether it helped.
    5. Use a second project to test isolation and portability. Choose broader scope from observed adoption.
    What to measure before setting targets

    Attribution coverage by cost and runs; source reconciliation gap; time to relevant context; learning reuse with outcome feedback; duplicate failure rate; review wait; lead time; rework.

    Set numerical success thresholds with the pilot owner after a baseline. No savings or targets are proven. Track planned, accepted, deployed and outcome-verified states separately.

    Tradeoffs worth keeping in view
    • Automatic capture versus trustworthy guidance: capture now, promote after validation.
    • Strict traceability versus developer flow: background linkage, gates at durable mutations, recorded exceptions.
    • Shared learning versus customer separation: scoped retrieval and reviewed publication.
    • More generation versus review capacity: observe queues before recommending more budget.
    • Unified access versus varied tools: discover capabilities and validate client support.

    The first proof is a handoff.

    One teammate leaves a useful lesson. Another retrieves it. One shipped change has a complete evidence chain. That is a testable start.

    Still unresolved: first buyer and champion, installation appetite, project sharing rules, dominant harness/tracker, credible outcome valuation, and whether learning or evidence drives adoption.
