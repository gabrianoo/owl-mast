## Ponytail: implemented personal/project telemetry

- **Scope and collection:** The Claude Code band tracks task cost, tokens, agent time, code reuse and tests following the latest change. Board aggregates tasks across projects, defaulting to local storage under `~/.config/ponytail/band/`. An import command adds historical Claude sessions with cost/time/tokens. The band requires Claude Code 2.1.290+, supports terminal and desktop, and excludes VS Code chat, cloud sessions and `claude -p`. Task Markdown copying is documented. These are maintainer claims, not measured reliability. [P1]
- **Exact board implementation:** A self-contained HTML renderer consumes CSV ledgers and embeds task JSON. Project and 7/30/90-day/all-time filters drive four KPIs (sessions, time, cost, tokens), a per-project/day chart and searchable sessions table (time, cost, tokens, turns, tests). Activity represents agent time over 84 days; current streak starts today if active, otherwise yesterday, and longest streak is calculated within that window. Imported sessions without test records show a dash. PNG (1200×630) and SVG share-card downloads are implemented. Footer identifies cost as Claude Code’s API-priced `/cost`, not billing. This verifies file-based ingestion and image exports, not a supported external telemetry API or webhook. [P2]
- **Visual inspection:** I opened the public PNG. It shows a dark left project rail, four colored KPI cards with small trend charts and period comparisons, a large stacked area chart with project-color legend and session dots, then a sessions table alongside a hexagonal activity heatmap. Active-days and streak figures sit beneath the heatmap. The visible example is 61 sessions, 20h13m, $285.30, 492.5M tokens and a 13-day streak. These are screenshot example values, not customer performance evidence. No T3 screenshot was inspected. [P3]
- **Website caveat:** The Apposters page presents agent-behavior/install instructions and claims 54% less code, 20% lower cost and 27% faster development. Its retrieved text does not establish dashboard behavior; use source and repository documentation for that. Its official affiliation was not established. [P4]

## T3 Code: multi-environment usage and inbound automation

- **Dashboard and scope:** Usage documents Codex, Claude Code, Grok Build, OpenCode, Antigravity and Cursor histories across connected environments. It exposes token/cache/model breakdowns, estimated API-equivalent cost, speed premiums, per-model trends/cache hit/cost-per-million, and configurable prices. Costs explicitly are not subscription bills. Environment filtering and partial scan results are documented. Shared history directories and repeated Cursor accounts are deduplicated. Cursor uses its dashboard API through the server’s CLI login; OpenCode/Antigravity read local databases. Coverage depends on accessible history; incomplete Grok records are missing. [T1]
- **Documented layout, not visually inspected:** Cost/Tokens/Limits views have 24-hour/7/30/90-day periods for the first two. Limits aggregates subscription accounts into window cards with per-account bar segments, reset information and account details. This is a strong reference for separating monetary estimates from actual quota availability. Streaks, activity heatmaps and usage exports were not established by this inspected document. [T1]
- **Webhook contract:** An On-webhook task accepts a request at its task URL; a public URL needs a T3 Connect managed tunnel. Prompt templates select JSON/form `{{body.path}}`, `{{headers.name}}`, `{{query.name}}`, raw `{{body}}`, or complete `{{request}}`; the example maps `{{body.pull_request.html_url}}` into a review request. There is no universal outbound telemetry event shape established here. GitHub signature verification supports `x-hub-signature-256`, hex encoding and `sha256=`. Request values are labeled untrusted; the docs explicitly say this is not a guarantee against malicious instructions. Filters gate execution. Duplicate-request keys suppress repeated keys for seven days; coalescing uses the latest payload over 10–3600 seconds and survives restart. Deliveries shows requests and produced prompts. Optional offline holding stores bodies via T3 Connect for up to 24 hours. This is an inbound agent trigger, not verified evidence-stream export. [T2]

## Reuse and product implications

- **License evidence:** Both repositories carry MIT licenses permitting use, modification, distribution, sublicensing and sale, with copyright/permission notices retained and no warranty. Ponytail names DietrichGebert; T3 names T3 Tools Inc. Reusing covered code is therefore feasible on those stated terms; dependency and asset coverage would need examination for a chosen implementation. [P5, T3; license-text conclusion]
- **Design inference:** Ponytail provides a compact overview-to-session-evidence visual hierarchy; T3 provides multi-environment/account aggregation, pricing semantics and reliable inbound-trigger patterns. For an organization product, connect such observations to explicit person/team/repository/delivery identifiers rather than interpreting tokens, spend or streaks as productivity. This is a proposed design direction, not a claim that either product implements it. [P2, P3, T1, T2; inference, medium]
- **Unresolved:** A supported organization-wide telemetry export/API, outgoing event webhooks, enterprise access controls, durable knowledge graph, and comprehensive delivery-evidence model were not verified for either product in this bounded pass. Ponytail CSV/embedded JSON are implementation formats; T3’s provider API consumption is not proof of a public T3 reporting API. Further adapter work needs an explicit contract and provenance review. [P2, T1, T2; research boundary, not absence claim]
