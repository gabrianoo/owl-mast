## Intent

**Problem:** `docs/engineering-tracking.md` forbids unattended story execution until a bridge is qualified: installed `bmad-loop` 0.13.2 only reads local sprint/stories/tickets queues, its parser rejects `E01`/`OM-01.01` IDs, its probes/verify commands are empty and its CLI adapters ignore reasoning effort, so nothing today lets a T3 coordinator dispatch, synchronize and gate story work with GitHub Issues/Projects as the progress authority.

**Approach:** Add a small, dependency-free Python tool (`automation/unattended`) that reads the actual GitHub backlog and Project, verifies the stable mapping (19 epics, 85 stories, 340 tasks, native parent links, `Depends on` lines), decides eligibility fail-closed, and drives a machine-owned per-story checkpoint/journal state machine whose only GitHub effect is an idempotent, append-only marker comment per operation; Project Status stays owner-written because GitHub offers no compare-and-swap. T3 remains the sole coordinator: the tool validates T3 task receipts (Claude Fable 5.1 `effort=high` implementer, fresh Codex GPT-6 Astra `reasoningEffort=high` reviewer), enforces checks-before-review, SHA-bound approval, at most two repair rounds, one implementer per story and cancel/resume/stop controls. Tracking identifier: GitHub issue #106 (ENG-01), outside OM numbering.

## Boundaries & Constraints

**Always:** Keep the product `SPEC.md`, epics, stories, task IDs and issue bodies unchanged. GitHub owns progress; the machine writes only append-only marker comments (`claim`, `release`, `block`, `proposal`, `probe`), never Project Status, issue bodies, checkboxes or issue state; all Status values, closing issues and ticking task checkboxes stay owner actions, and task completion reaches GitHub only as an evidence proposal naming the exact commit. Every admission and every effect re-reads the revisions it depends on (issue, body, close reason, Project item, Status) and refuses on any change; because GitHub exposes no compare-and-swap, no owner field is ever overwritten. Unknown eligibility, denied permission, outage, parse failure, missing Project item or a receipt that lacks the required model/effort fails closed and never advances state. Credentials come only from the `gh` CLI session (or `GH_TOKEN` provided through the supported secret path); the policy file refuses secret-like keys. Exclude E17 and E19 from default dispatch; dispatch only stories in an explicit allowlist with `Ready` status and `Done`+closed dependencies, except designated contract-design portions listed in policy.

**Never:** Merge, deploy, release, schedule, enable a persistent loop, start product stories (OM-01.02 remains separately authorized), edit issue bodies or checkboxes, close issues, write sprint-status.yaml, run or wrap the `bmad-loop` CLI, store tokens in config or state, claim live-transport qualification from fixture tests, or present fixture coverage as qualification before independent review.
