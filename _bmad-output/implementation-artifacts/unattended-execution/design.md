# ENG-01 design: state machine, writers and guarantees (remediation pass 1, repair pass 2)

> **Supersession (2026-11-06).** The owner accepted the trusted-machine operating agreement (`../spec-eng-01-trusted-operation.md`). Where this document lists hard child deadline/resource bounds, credential confinement, denial-tested bounded credentials or automated Project Status synchronization as *prerequisites*, they are now accepted residual risks or manual owner steps; the controls, refusals and guards described here remain in force and nothing historical below is rewritten. Activation remains disabled.

Companion to `../spec-unattended-execution-foundation.md` and `../spec-eng-01-remediation-pass-1.md`. Operator guide: `docs/unattended-execution.md`. This revision follows two independent review rounds and the final disposition of PR #107 (six verified defects on head `a0fa769e`): the machine never writes Project Status; every effect is a write-ahead intent with a stable operation identity and its complete payload whose completion and transition persist in one write; task capacity is authorized durably before every launch and consumed by the receipt bind to the exact authorization; an issued authorization is an ownership obligation until its exact receipt plus terminal evidence or a positive no-launch reconciliation; the active task is tracked independently of the phase and released only by terminal evidence for exactly that task; a terminal story or a cancelled run abandons and never replays advancing intents; duplicate stable ids are refused before any dictionary reduction; evidence gates re-read the actual worktree; operations are serialized by a store lock; run state is bound to its environment; and every state command refuses the real transport.

## Story phases

```
reserve ──(admission under lock, unique ids, revisions re-read, implementer authorization, claim marker)──> claim-incomplete ──(marker exactly once; completion + phase in one write)──> reserved
reserved ──bind-receipt --authorization <id> (receipt validated, worktree identity, exact authorization consumed)──> claimed   active task: implementer
claimed ──record-head (+ implementer terminal evidence)──> implemented                                                active task: none
implemented ──run-checks (no active task, full set, exact clean HEAD, HEAD re-checked)──> checks-passed | checks-failed
checks-passed ──authorize-review (worktree re-read, no active task, reviewer authorization)──> review-authorized
review-authorized ──bind-receipt (fresh reviewer receipt)──> review-requested                                          active task: reviewer
review-requested ──record-review (+ reviewer terminal evidence, worktree re-read)──> review-approved | changes-requested   active task: none
checks-failed | changes-requested ──authorize-repair (no active task, round ≤ 2 counted here, authorization)──> repair-authorized ; round 3 ──> blocked
repair-authorized ──bind-receipt (fresh implementer receipt)──> claimed                                               active task: implementer
checks-failed | changes-requested | repair-authorized ──record-head──> REFUSED (repair-required)
review-authorized | review-requested | review-approved ──record-head(new sha)──> implemented (approval invalidated, pending proposal abandoned, pending review authorization REVOKED but still owned; active task untouched)
any evidence gate with unreported worktree change ──> implemented (same invalidation; active task untouched)
any phase with an unresolved (pending or revoked) authorization ──cancel | block | cancel-run | run-checks | authorize-* | propose──> REFUSED (authorization-unresolved; a pending one is revoked durably); its late receipt ──bind-receipt──> same phase, task owned for cleanup only; record-no-launch (exact id) ──> resolved not-launched
review-approved ──propose-evidence (approved == head == sha, no active task, revisions, worktree, PR head/reviews/checks; completion + phase in one write)──> proposed
any active | conflict ──block | cancel (terminal evidence for exactly the active task; no unresolved authorization, or its no-launch attestation; pending advancing intents abandoned in the same write)──> blocked | cancelled
duplicate marker on any effect (first run or resume) ──> conflict
```

`proposed`, `blocked`, `cancelled` and `conflict` are terminal for the machine; no advancing intent is ever replayed from them. A cancelled run (`run-cancelled`) or a run past its wall-clock budget (`wall-clock-exceeded`, a local expiry that stops no child) refuses every advancing operation, returns or issues no authorization, binds a receipt for an earlier authorization for cleanup only, and keeps stories with an active task owned until their terminal evidence. A story is admitted at most once per run; a later run may admit it after the release marker. `Done`, closing the issue, ticking tasks, Project Status, merging and deploying are owner or GitHub facts the machine reads and never writes.

## External effects and their identity

| Local event | GitHub effect | Operation id | Payload and recovery |
| --- | --- | --- | --- |
| reserve | comment `kind=claim` | `claim` | body persisted with the intent; preconditions = revisions; completion and `reserved` persist in one write; pending ⇒ re-verified then replayed on resume only while the story is active and the run neither cancelled nor past its wall clock; revisions changed before completion ⇒ the story is cancelled and, when one or more claim markers landed, the owed `release` intent is saved in the same write and posted idempotently (zero markers ⇒ no release owed); exactly one marker required; foreign unreleased claim ⇒ refuse |
| propose-evidence | comment `kind=proposal sha=… pr=…` | `proposal-<sha12>-pr<n>` | body persisted; preconditions = sha, pr, revisions; completion and `proposed` persist in one write; replay only with a current local approval for exactly that sha (phase, approved and head SHA, no active task) and after revisions, worktree and PR (head, all review pages, checks) re-verify; local changes-requested, new head, invalidation, GitHub regression, cancel/block or a cancelled run ⇒ intent abandoned, nothing posted; a re-approval at the same commit reuses the operation id |
| block | comment `kind=block` | `block` | phase, intent and the abandonment of pending advancing intents saved in one write; failure recorded; replayed on resume |
| cancel | comment `kind=release` | `release` | as block; requires terminal evidence for exactly the active task |
| authorize-review / authorize-repair, bind-receipt, record-task-terminal, record-no-launch, head, checks, review verdict | none | — | local checkpoint + journal; authorizations (and their resolutions), receipts, terminal evidence, no-launch attestations and commit SHAs are the evidence |

## Precise guarantees

1. **Revisions before admission and before effects.** `reserve` compares the plan snapshot's revisions of the closure against a fresh read and refuses on any difference; the fresh decision must also be dispatchable. `propose-evidence`, a proposal replay and `resume` compare against the revisions recorded at admission. No revision is ever replaced implicitly; `rebase-revisions` is explicit and journaled.
2. **One writer per field.** The machine appends comments only. Project Status synchronization is not implemented because GitHub offers no compare-and-swap and the field belongs to the owner.
3. **Stable operation identity with payload.** Every effect is a write-ahead intent keyed by operation id, carrying its marker and complete body. Retries and restarts find the intent and post that body. Zero markers ⇒ post, one ⇒ adopt, more than one ⇒ `conflict`.
4. **Terminal atomicity.** `block` and `cancel` save the terminal phase, the cleanup intent, the abandonment of every pending advancing intent and the resolution of the story's authorization in a single atomic write before posting; a crash anywhere afterwards leaves a pending cleanup that `resume` replays and no advancing intent that could ever be replayed. They never run while an authorization is unresolved (see 16).
5. **Restart order.** `resume` refuses on the live transport, validates the worktree identity before any effect, replays pending cleanups, then reconciles completed intents whose transition did not persist only behind the guards of a fresh attempt: a done claim in `claim-incomplete` becomes `reserved` only in a run that is not cancelled and only if its revisions are unchanged (changed ⇒ cancelled with the release it owes); a done proposal becomes `proposed` only in a run that is neither cancelled nor past its wall clock, with phase `review-approved`, approved and head SHA equal to its SHA, no active task and no unresolved authorization, and only after the fresh revisions (with unique identities), the re-read worktree and the PR (head, all review pages, checks) re-verify exactly as for a fresh proposal, with the same consequences (stale ⇒ refused, dirty ⇒ `implemented`, objection ⇒ `changes-requested`, outage/denial/duplicate id ⇒ refused). Otherwise the effect stays recorded as history (`reconciliation-withheld` journaled), is never reposted, the phase is not advanced and `cancel`/`cancel-run` finish the story. Then it abandons pending advancing intents of a terminal story or a stopped run (cancelled or past the wall clock), re-verifies the remaining ones (claim: revisions, changed ⇒ cancelled with its release; proposal: current phase and exact-SHA approval with no active task, then revisions, worktree, PR) before posting their persisted body, then refuses active phases whose revisions changed.
6. **Serialization and binding.** Every operation holds the store lock and reloads run accounting inside it. A run is bound to its repository, policy digest and environment (`fixture` or `live`); reopening with another refuses before recovery, so fixture-born state can never drive production. A story file with another schema is refused.
7. **Authorization before delegation; no reclaim.** `reserve`, `authorize-review` and `authorize-repair` issue a durable task authorization under the lock before any task exists and refuse when `max_delegated_tasks` would be exceeded or the wall clock has passed (the pending authorization is then neither returned nor re-issued and stays spent); an issued authorization is spent whether or not it is bound (a `not-launched` resolution refunds nothing, not even a repair round); `bind-receipt` consumes exactly the authorization named by `--authorization` (a wrong or stale id is refused `authorization-mismatch`; without the flag the single unresolved authorization is the only candidate, since none is issued while one is unresolved) and requires a task id never bound anywhere in the run (any story, any role, terminal or not); a reviewer receipt records the SHA of its authorization, never the current head; after the run stopped (cancelled or expired), or after the authorization was revoked, a receipt binds for cleanup only: slot spent, id bound, task owned, phase unchanged, call refused with `bound_for_cleanup`; budgets (stories, authorizations, repair rounds) are derived from the story files, never from cached counters; a story has at most one state per run.
8. **Budgeted repair.** After `checks-failed` or `changes-requested` only `authorize-repair` (round counted at authorization) followed by `bind-receipt` returns the story to `claimed`; `record-head` is refused.
9. **Executed checks and re-read worktree.** `run-checks` requires the claimed worktree, HEAD equal to the recorded sha, a clean tree, runs the full configured set and re-checks HEAD and cleanliness. `authorize-review`, `record-review` and `propose-evidence` (first attempt and replay) re-read the worktree identity, HEAD and cleanliness; an unreported change invalidates check and review evidence (phase `implemented`, head set to the actual HEAD, pending proposal and review authorization abandoned, active task untouched).
10. **Per-reviewer objections over all pages.** Reviews are read until `pageInfo.hasNextPage` is false; a malformed page, a changed total or a count below the total refuses. A reviewer's latest effective review (`APPROVED`, `CHANGES_REQUESTED`, `DISMISSED`) at any commit decides.
11. **Ownership until terminal evidence.** The active task (`active_task`: id, role, authorization) is independent of the phase and of HEAD notifications. `record-head` requires the implementer's terminal evidence while it is active and never touches an active reviewer; `record-review` requires the reviewer's; `run-checks`, `authorize-review`, `authorize-repair` and `propose-evidence` require no active task; `cancel`/`block`/`record-task-terminal` require `{taskId, status}` matching exactly the active task with a terminal status; `cancel-run` stops admissions, releases the stories without an active task and reports the rest; a cancelled or expired run refuses every advancing operation while still accepting terminal evidence and cleanup.
12. **Unique identity.** A stable id carried by more than one issue, in the plan snapshot or in any fresh read (admission, proposal, resume, rebase), refuses with `ambiguous-identity` before any `by_id` reduction; `plan` reports it per story.
13. **Fail closed.** Unknown declarations, unknown close reasons, duplicate ids, missing Project items, inconsistent issue state, `PermissionDenied`, `Outage`, `NotFound`, unknown transport errors, binding, environment, schema and worktree mismatches refuse without advancing.
14. **Live gate.** Every state-advancing operation and every recovery refuses a live transport with `live-execution-disabled` and the verified gaps. The only live write is the comment-only probe on `engineering-automation` issues.
15. **Wall clock is a local expiry, not a child bound.** `max_wall_clock_minutes` bounds what this tool authorizes and advances; it cannot stop a delegated child (T3 `timeoutMs` bounds the wait only). A launched worker is owned until its terminal evidence regardless of the deadline.
16. **An issued authorization is an ownership obligation until it is resolved.** Statuses: `pending` (authorizes work; its receipt binds into work) → `revoked` (story cancel/block/cancel-run requested, evidence invalidated by a new head or an unreported worktree change: no work is authorized, but a task may have been launched) → `consumed` (the exact receipt was bound; ownership continues as the active task) or `not-launched` (positive reconciliation). At most one authorization per story is unresolved (pending or revoked), because `_authorize` issues none while one is; so a late receipt can never land on a successor slot, and the explicit id is checked on top. While one is unresolved: `cancel`, `block` and the per-story part of `cancel-run` refuse `authorization-unresolved` (revoking a pending one durably in the same call, so that the receipt can only bind for cleanup; `cancel-run` lists the story as awaiting), no release or block marker is posted, the claim stays visible to other runs, the concurrency slot stays held, `run-checks`, `authorize-review`, `authorize-repair` and `propose-evidence` refuse. Honest no-launch evidence is limited to what exists: (a) the coordinator's explicit attestation `record-no-launch {"authorization": "<exact id>", "reason"}` (inline on `cancel`/`block`/`cancel-run` as `--no-launch`), a report at the same trust level as receipts and terminal evidence, applicable once and never to a consumed authorization; (b) the structural proof that the reservation never returned (`claim-incomplete`, or `conflict` entered from it): the protocol launches only after `reserve` reports `reserved`, so the implementation authorization of an unreturned reservation is resolved `not-launched` without an attestation. No T3 attestation or hidden API is assumed; when neither exists the story stays owned and the only exits are the late receipt plus that task's terminal evidence or the attestation. Everything is durable (schema 3) and idempotent across restarts and retries.

## What the tool cannot see (explicit limits)

- A launch is not an event the tool observes: it bounds what can be bound. A task launched without an authorization, or two launches for one authorization, leave an orphan the coordinator must `task_cancel`; the tool refuses to bind the second. Whether a task was launched for an authorization whose receipt never arrived is equally invisible; the tool therefore keeps the authorization owned until the receipt or the coordinator's no-launch attestation, and cannot release the story on its own.
- Receipts, terminal evidence and no-launch attestations are the coordinator's reports of `delegate_task`, `task_status` and `task_cancel` results (or of a `delegate_task` never issued); a false report is not detectable.
- No child deadline, resource bound or credential confinement exists in the installed T3 tools; `timeoutMs` bounds only the coordinator's wait.

## Why not bmad-loop

`bmad-loop` 0.13.2 dispatches from `sprint-status.yaml`, `stories.yaml` or a `tickets.py` tree, none of which is GitHub; its sprint key grammar `N-M-slug` and the sprint parser's `Epic N`/`Story N.M` headings reject `E01`/`OM-01.01`; `[verify]`/`[environment]` entries are empty; tmux CLI adapters ignore `effort`; its merge-back and cleanup act on local branches. The foundation keeps T3 as the sole coordinator and stores machine state under `.unattended-runs/`, separate from `.bmad-loop/`, which stays untouched.
